# 交付、运行与受控改进协议

适用：将本次实现交给实际使用者或运行环境。单机工具与长期服务都按自身承诺验收，不把生产工程等同某个基础设施产品。

## 进入阶段前

确认本次承诺、代码与依赖版本、目标环境和实际启动入口、已有测试、在途任务/旧数据、回退范围和运行责任。复用 [证据工作流](../evidence-workflow.md) 对应协议与改动，不凭测试名推断隔离或覆盖。

## 部署适配

本地工具、单机服务、托管平台、容器编排都可以是合理终点。选择由容量、故障目标、网络/隔离、运维能力与成本决定，不把 Kubernetes 当毕业条件。

明确运行角色、启动方式、依赖版本、配置验证、秘密注入、持久路径、优雅退出与升级。API/Worker 是否分进程取决于延迟、隔离和伸缩；托管引擎已有角色时沿用。

存活、就绪与下游降级不是同一信号。供应商暂不可用不一定应反复重启自身。停止领取新任务、保存进度、释放容量、排空在途任务与强制截止需要协调。

使用容器时检查构建上下文排除秘密、最小权限、卷/网络和真实健康条件；启动顺序不等于依赖就绪。已有平台提供的能力应验证配置，不再复制一份应用层实现。

## 版本与在途任务

追溯实际影响行为的配置：代码/运行时、模型、prompt、工具描述/schema、策略、图定义/reducer、checkpoint/事件/消息格式、检索数据与评测集。按关联形成版本清单即可，不强制每张表复制全部字段。

版本标识对应可重现内容；同名版本被覆盖会破坏审批与评测证据。恢复旧任务时区分历史配置快照与当前强制安全限制，不能用旧批准绕过已撤权或停用工具。

迁移应考虑“新代码读旧状态”和“回退代码读已写新状态”。可采用兼容新增、分阶段部署、受控回填、确认旧读者/在途任务退出后清理，也可使用引擎提供的版本路由。具体流程按平台，不强制同一迁移工具。

回滚镜像不能撤销外部动作，也不能自动撤销数据库结构。破坏性变更需要明确备份、恢复、前向修复或保留旧处理器方案。正常创建的输入、历史和审计不要为适配新版本而无声改写。

## 发布与验证

发布保护按风险选择：本地检查、staging、shadow、内部用户、灰度、feature flag、工具停用、队列暂停、排空和回退。不要机械要求每个项目都有全部环境或固定流量比例。

从承诺反推测试：

| 测试面 | 证明的行为 |
|---|---|
| 规则/合同 | 状态、schema、权限、错误分类符合约定 |
| 集成 | 真实入口调用到正确适配器，记录与输出一致 |
| 并发/重复 | 原子更新、重复受理、节点/消息重试没有不允许的效果 |
| 故障/恢复 | 关键边界退出、响应丢失、等待/取消、预算耗尽有正确结局 |
| 兼容/迁移 | 旧快照、历史、消息、客户端与新旧处理器可协作 |
| 负载 | 在指定任务分布与依赖行为下，容量/SLO 满足目标 |
| 备份恢复 | 数据/索引/引用/未决动作能在规定目标内恢复并核对 |

不是每项改动都跑全套。明确实际执行的测试环境与证据，避免把静态代码审查、语法检查和真实集成验收混为一谈。

交接使用 [承诺到交付证据](../evidence-workflow.md)：把实际入口、依赖配置、关键故障断言和结果关联到本次承诺。对账关注 [业务终局与持续核实](tool-execution.md#未决结果业务完成与持续对账)，不把下游受理或执行器完成直接当成业务完成。

## 运行手册模板

需要值班的系统，按真实依赖写可操作手册：症状与影响→先看的查询/指标/日志→关键分诊→止损→恢复→验证→升级联系人→复盘。不存在的 debug 端点不要写成已经可用。

常见分诊方向：

- **积压**：分辨执行者不足、下游慢、数据库瓶颈、provider 限制；扩容不是唯一答案。
- **执行停滞**：看当前所有权、最后可靠事实、等待原因、未决动作，再决定恢复；不批量重跑所有“running”。
- **写工具失败/未知**：先控制新风险，再按操作身份核实；别用重发验证是否成功。
- **模型错误或成本异常**：按任务/版本定位轮次、repair、重试与 fallback；保留已计费事实。
- **输出断线**：区分执行故障与展示故障，按游标/快照恢复展示。
- **迁移/发布失败**：停止继续扩散，核对实际格式与运行版本，选择兼容回退或前向修复。

灾备范围包括主数据、执行历史/快照、对象引用、密钥恢复流程与未决外部动作。设定 RPO/RTO 并演练；备份任务成功不等于已经证明可恢复。

## 反馈、评测与改进

执行正确性与业务质量用两把尺子。可结合用户反馈、人工纠正、工具失败、下游业务结果和事故，而非只看 `succeeded` 或满意度。迟到结果也可能推翻原评价。

把样本加工成可评测案例：允许用途与访问范围→有界抽取→必要脱敏→保留来源关联→人工或可靠规则确定期望→冻结版本。错误动作不能因曾成功执行就作为正确训练标签；外部依赖故障也不能一律归因模型。

至少区分决策/工具参数、业务约束与授权、答案质量、回归、成本/延迟。图和多 Agent 不应要求与基线完全相同的节点/工具顺序；除非顺序本身是约束，应检查结果和必须满足的过程条件。

评测开始前注入 fake/sandbox/录制回放适配器并限制真实凭据/出口。只改 prompt 写“这是测试”不构成隔离。只读历史展示与会执行候选代码的评测不同。

候选与基线在可比输入、固定数据和明确配置上比较；记录随机性、样本规模与不同任务分布，有限样本零违规不证明全域安全。高风险约束独立设门槛，不能用平均质量分抵消。

自动改进可以产建议、差异和证据；能否自动生效由项目授权与风险政策决定。高影响权限/工具/业务策略变更通常需要具体审核与受控放量；低风险文案也可有明确自动发布规则。审批和评测绑定同一候选内容，修改后重新验证相应范围。

小项目可用版本化场景文件与测试脚本，不必创建完整反馈数据库、自优化服务或训练平台。确需训练导出时才设计用途授权、敏感性、质量、导出去向与审批留痕；不能把线上原始轨迹直接上传作为默认步骤。

## 应整理的产物与退出条件

交付运行方式/配置、版本与迁移说明、真实入口证据、已运行检查及未验证项、必要的处置/回退和后续改进。已有流水线、运行手册与平台记录可直接引用。

本次完成意味着授权范围内的代码与适用协议相符，关键故障窗口有相应证据；真实依赖缺席时注明阻止验证的承诺。不要把“新增表/状态/队列/账本”或文档检查通过当成生产认证。
