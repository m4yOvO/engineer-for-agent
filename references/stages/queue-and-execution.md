# 队列、调度与执行权协议

适用：异步受理、削峰、多个执行者、长任务或可靠交接。先验证已有工作流/托管平台是否承担相同责任；有界同步调用可以不引入队列。

按 [共用适配规则](../engineering-workflow.md#逐条适配与项目记录) 选择本阶段条目。

## 进入阶段前

确认成功受理的承诺、工作粒度、持久性、吞吐/延迟、顺序范围、重复投递、并发和恢复目标。区分业务命令、可执行工作单元、消息投递和 Worker 尝试；不能用消息被取走代表任务成功。

## 受理到执行的交接

当承诺“接受后不会因进程退出丢失工作”，受理确认必须对应可恢复的事实或平台确认。

| 实现选择 | 合适前提 | 必须解释 |
|---|---|---|
| 同步直接调用 | 调用有界，调用者承担断线/重试合同 | 连接终止与在途副作用的关系 |
| 单一持久队列/数据库任务 | 一个存储可同时受理和保存调度状态 | 原子领取、重试、确认、清理和容量 |
| 数据库 + 外部 Broker | 两个系统没有共同原子提交 | Outbox/CDC/等价恢复策略；发布成功但本地标记失败会重复 |
| 工作流/托管平台 | 平台承担持久受理与派工 | API 确认语义、连接/配置、任务保留与恢复范围 |

Outbox 是解决一个具体提交窗口的方法，不是每个 Agent 的必备表。若使用它，意图与业务受理同事务，独立发布后再确认；重复发布交给下游去重。任务消息通常带引用和版本，避免携带将过期的权威完整状态；不可变输入快照等场景可以带载荷，说明范围即可。

持久结果先于消息确认；某次消息处理完成不等于整个业务任务成功。已经进入等待或被可靠安排重试，也可以结束本次消息处理。

## 消息从哪里来、何时确认

| 环节 | 必须明确的合同 |
|---|---|
| 生产/受理 | 接口确认对应什么持久事实；响应丢失后如何查询/去重 |
| 发布/交接 | 单存储原子调度、可靠平台确认或跨系统恢复机制；发布成功但本地未确认如何重投 |
| 领取 | 原子 claim/visibility/lease、并发与公平配额；领取时复核任务有效期、当前状态和权限 |
| 处理 | 每次投递映射到稳定工作身份，旧消息不能覆盖新一代执行；在途工具按原操作身份处理 |
| 完成/ACK | 本次工作的结果或可恢复的等待/重试交接已可靠保存后 ACK；ACK 丢失导致重投时复用事实 |
| 重试/死信 | 分类、唯一重试拥有者、退避/截止/次数、死信/人工出口；重投仍维持业务防重身份 |
| 停机/接管 | 停领、保存/排空、超时与可见性/租约续期，接管后拒绝旧写者；不因 kill Worker 推断外部动作未执行 |

消息可以携带引用或不可变快照。说明 schema/版本、工作 ID、主体/资源引用、执行代次及有效期等实际必要字段；可信身份由消费方验证，不凭消息里自报租户授权。传输 message_id 是否稳定由平台合同决定，不能直接当成业务操作 ID。

顺序保证注明按哪个分区/实体/actor/工作流生效；不要由单分区有序推出全局有序。消费完成顺序可能不同于领取顺序，业务守卫仍需处理旧版本消息。

## 执行权与故障拥有者

同一业务状态有并发写者时，需要数据库条件更新、版本/CAS、锁、单写 actor 或引擎等价机制。租约过期只表示没有及时续约，不证明旧进程已死。

自建租约需设计：原子领取、续约、代次/栅栏、过期接管、旧写者拒绝、终止清理。扫描器提交前重新核对条件；旧执行者写入要验证所有权。外部系统不接受栅栏时，依然需要业务防重；两个进程各自认为有权并不意味着能重复动作。

每种失败指定拥有者，避免 API、SDK、节点、Worker 和队列同时做完整重试：

| 情况 | 通常的处理方向 |
|---|---|
| 输入/权限/业务条件拒绝 | 返回明确拒绝，原样重试通常无效 |
| 已确认未执行的临时失败 | 在合同允许时退避、抖动、次数/截止与预算限制 |
| 只读调用超时 | 按业务允许程度有限重试，仍考虑费用和负载 |
| 写操作结果未知 | 根据同一操作身份核实，或按已验证的下游幂等合同重发；否则等待/人工处理 |
| 用户取消或引擎中断 | 按控制流处理，不能吞掉并伪装成功，也不默认当可重试错误 |
| 基础设施损坏 | 保存证据、按调度职责恢复或降级；不要覆盖已有业务事实 |

SDK 内部重试会放大实际次数。定义 attempt 是一次外部尝试、一次节点执行还是一次任务代次，并对整体工作限制累计消耗。耗尽之后保存可排查信息，有明确失败、死信、人工接管或延迟处理出口。

租约/visibility 的时间不是业务 deadline。执行者超过租约仍可能运行，延长可见性不提供外部系统的防重；按 [工具协议](tool-execution.md) 处理外部效果。人工等待应保存现场并释放昂贵容量，不能靠常驻 Worker 等待用户。

## 容量、积压和处置

按项目选在途并发、入口限流、队列长度/最老消息年龄、用户/组公平性、优先级与背压。区分下游限流、执行器不足和热点串行；先核实瓶颈再扩容。过期工作不得因积压后重投重新获得完整时间或预算。

死信可存拒绝原因、稳定身份、版本和最后证据。重放/重新入队要先检查当前权限、有效期、状态和未决副作用；只能在授权范围内操作，不能用全量重跑消除未知。

## 应整理的产物与验收

按实际调度路径描述交接、执行与确认；应用直管消息时展开消息合同、重试/所有权和容量故障处置，平台托管时引用其责任及配置，不要求应用暴露相同的发布/领取/ACK API。未采用队列时说明同步或其他执行方式的边界，无需提交消息表、租约或死信设计。

从实际机制中选择受理后退出、发布确认丢失、并发重复消费、Worker 租约过期后晚写、ACK 丢失、过期消息、毒消息、下游慢与优雅停机等适用窗口验证。持久受理核对已接受工作不丢；允许丢弃的工作核对丢弃边界和调用者可见结果。尝试数、业务允许的重复语义和等待/重试出口按各自合同验收，不以队列深度归零代表业务成功。
