# 状态机、图与生命周期协议

适用：任务有多步骤、等待、重试、取消、恢复或并发推进。显式 FSM、图路由、actor、工作流历史均可表达这些合同；不要求建一张统一状态表。

条目、产物和验收均按 [逐条适配规则](../engineering-workflow.md#逐条适配与项目记录) 选择；本阶段适用不代表所有子项都需要。

## 进入阶段前

定义业务完成标准、执行形态、事实拥有者、可接受的中断结果、人工操作和外部效果。先区分执行进度、某次工具尝试、业务结果和观察投影；下游受理或工作流结束不自动等于业务最终完成。

## 状态和转移设计

状态命名由领域与引擎决定。列出可观察位置、事件/命令、守卫和效果，而不是只画状态节点：

| 当前状态/图位置 | 事件与可信操作者 | 前置条件/版本/所有权 | 共同提交的事实 | 下一位置及待办 | 确认/资源交接 | 重复、冲突、到期、失败 |
|---|---|---|---|---|---|---|
| 按项目填写 | 用户回复、定时、节点完成等 | 当前等待点、业务条件、当前授权 | 该转移需要哪些恢复依据 | 谁可靠推进下一步 | 何时可响应、何时旧执行者退出 | 哪个操作胜出、败者得到什么 |

- 不可达位置、无出口的等待、无界循环、重复结束以及非法转移需要明确处理。分层/并行状态和子图不强行压成单一 step_index。
- 图的守卫、条件边、reducer、并行合并与中断对应转移合同；框架负责的位置不再由另一套状态机任意回写。
- 执行终态只约束对应执行；同一 thread 的新任务、重开/分支有独立语义和 lineage。业务结果后续变化可更新业务投影，保留已结束执行的历史。
- 状态变化由条件更新、事务、单写者或引擎合同裁决；先读再分别写不能证明取消与继续只有一个胜者。

## 操作一致性契约

在要求持久控制的项目中，逐个定义适用操作的“前置条件/操作者 → 必须共同成立的事实 → 确认点 → 交接与资源释放 → 失败后下一步”。这是操作合同，状态名、物理记录和具体步骤由项目决定。

| 操作 | 要一起判断的事实与顺序 | 需要覆盖的竞争或失败 |
|---|---|---|
| 暂停/等待 | 当前执行权与待办动作；持久保存等待身份、恢复位置和相关批准依据，再确认可暂停并释放执行容量 | 等待标记已写但恢复现场未保存；回复早于释放旧执行者 |
| 继续/回复 | 身份与当前等待点匹配；条件性消费该等待输入，可靠安排继续，随后确认受理 | 同一回复重复提交；取消/过期与继续同时发生；输入已接受但唤醒丢失 |
| 取消 | 记录请求与裁决依据；按执行状态在安全边界停止后续推进，保留在途动作跟踪 | 取消与完成并发；取消确认被误解为外部动作已撤回 |
| 完成/失败收尾 | 所需输出或错误、执行结局和必需历史已经可靠保存，再确认本次消息处理与释放资源 | 输出已存但收尾失败；消息已确认而完成事实未保存；重复收尾 |

同一原子边界内必须一起成立的事实，用事务、条件写、引擎历史或其他已验证机制提交；可异步更新的投影单独注明延迟与修复责任。跨系统不要求不存在的分布式事务，但确认受理前必须已有可恢复的交接依据。

写清 ACK、租约/容量释放与下一次唤醒各由谁负责；持久等待不等于旧执行者已停止。旧执行者晚到的清理或写入不得释放/覆盖新一代所有权。继续与取消的胜者由原子裁决决定，落败请求返回可解释结果，不靠各自先读一次状态裁决。

若框架已原子记录 interrupt/signal/activity 完成，直接引用该合同和实际配置；不要另建竞争状态机或强制增加这些字段。测试按 [证据工作流](../evidence-workflow.md) 检查关键提交窗口。

## 恢复矩阵

需要恢复时，列出可能落盘的每一种现场和对应下一步，不只保存 `next_step`。

| 已有事实 | 恢复方向 |
|---|---|
| 仅有已接受输入 | 开始尚未完成的执行单元 |
| 已产生动作意图，未有可靠结果 | 查操作账本/下游事实，不能先生成另一个意图绕开旧动作 |
| 结果已完成，但上下文或状态投影未补齐 | 复用结果并完成本地收尾 |
| 图部分分支已持久完成 | 按引擎恢复语义接续剩余任务，校验 reducer/重复写与合并 |
| 处于等待 | 接受符合当前等待点的输入后继续，不靠常驻线程 sleep |
| 最终输出已保存 | 补终态/投影/通知等收尾，不重新生成业务动作 |
| 数据或版本不可读 | 停在可诊断状态，通过适配或人工处理，不能静默清空重跑 |

Checkpoint 的内容由执行器决定，可包含 channel 状态、消息投影、活动结果、待办动作、预算和配置版本。不是所有框架都需要完整对话快照；也不是写了快照就能消除外部成功、本地未记的窗口。

## 人工等待与取消

人工等待保存具体动作/问题、版本、等待身份、允许回复者和过期政策，释放执行槽。回复与当前等待点绑定，重复回复按合同去重；批准人身份来自认证，不能相信请求中的 `approved_by`。

批准应指向用户实际看过的内容或摘要，包括目标资源、动作、参数与相关版本。批准后改内容需要重新评估。执行前重新核实当前权限、kill switch、业务余额/资源状态等；历史配置快照用于追溯，不能绕过当前撤权。

不要求所有动作审批，低风险自动执行可以是合理政策。涉及并行或多 Agent 时分别定义谁提出、谁批准、谁执行、预算归属和父子取消传播。

取消至少区分已接收取消请求、停止未来推进、外部在途动作已明确结束。实际状态名称自定。取消后可能仍有已发生或未知动作，保留审计并继续核实；不要把按钮“已取消”说成所有外部变化已撤销。

## 重放与重开

| 行为 | 需明确的合同 |
|---|---|
| 只读历史展示 | 只读记录，不调用模型/工具产生新行为 |
| 引擎 replay / time travel | 依框架可能重入代码、复用结果或继续执行；先核对语义，不等同只读展示 |
| retry / resume / restart | 哪一执行或尝试继续、哪些结果复用、哪些代码可能重跑 |
| rerun / fork / reset / repair | 新意图还是旧意图；历史与 lineage 如何保留；哪些副作用和权限边界不变 |

为 UI 与管理接口使用不含糊的操作名，并提供效果预览；框架名称与产品名称不同是正常的。

## 应整理的产物与验收

按实际控制路径整理状态/路由、转移条件及事实拥有者，可直接引用图定义、引擎合同或代码位置；简单同步模块可用几行说明。只为项目支持或承诺的等待、过期、取消、恢复与旧版本读取展开相应合同和验收，恢复矩阵仅在存在恢复需求时展开。未提供的产品操作说明边界；真实执行中会发生的异常和未决效果仍须有处置。

按适用性验证重复/过期命令、取消与继续/完成竞争、暂停提交失败、旧执行者晚到、部分分支恢复、无出口等待和旧版本现场。观察响应之外的状态、历史、恢复依据与容量释放；[工具结果](tool-execution.md)、[队列交接](queue-and-execution.md) 和 [时间](security-and-resources.md#超时截止与剩余时间) 使用各自协议。
