# /brainstorming：从需求到工程计划

目标是形成可执行的设计，而非先选一套服务模板。此模式可以给出接口、数据结构、伪代码和迁移方案，但不实现项目代码。

## 理解与取舍

从已有材料提取业务流程、限制和成功标准。只问会改变架构的问题，例如“任务是否必须在进程重启后继续”“动作能否撤销”“是否跨租户”。其余用明确假设继续，不用长问卷阻塞。

区分用户已要求的约束、仓库可验证的事实、为了推进采用的假设。假设有误会改变选型时，标出替代分支。

读取 [架构适配](architecture-adapters.md)，选择符合项目的组合。对真正有争议的选择比较两到三个可行方案，说明成本、失败语义和迁移难度；只有一个合理方案时无需凑选项。保留用户已有框架，除非有具体不满足的承诺。

走通一个代表性任务，标明入口、执行者、状态拥有者、外部依赖、结果交付及信任边界。再走一次失败或等待路径，解释中断后发生什么。复杂协作关系可用 Mermaid。

## 完整规划的内容

按 [能力地图](capability-map.md) 判断适用性，把以下内容组合成适合项目的文档；不要求每项独立成文件。

| 规划面 | 需要具体到什么程度 |
|---|---|
| 范围与成功 | 任务类别、业务完成条件、数据权限范围、延迟/吞吐/成本目标及依据、暂不承担的承诺 |
| 架构与边界 | 执行模型、状态拥有者、组件职责、同步/异步选择、复用平台能力及配置前提 |
| 入口与控制 | 按场景设计 HTTP/RPC/CLI/消息协议；身份、请求/响应、错误、重复请求、取消、等待/继续、结果/产物交付 |
| 数据与状态 | 实体、键、关系或引用、约束、查询/索引、保留与删除、事务边界、框架存储映射 |
| 运行与恢复 | 调度/并发、状态转移或图推进、持久化边界、失败分类、重试拥有者、恢复算法、人工交接、未决动作 |
| 模型与工具 | 模型适配合同、工具能力表、可信输入来源、授权、业务动作身份、未知结果处理、审批/隔离与审计 |
| 资源与安全 | 数据访问与出口、运行环境、密钥、记忆/RAG、限额与预算执行点、长任务资源释放 |
| 观察与运维 | 状态/事件/日志/指标/Trace 分工、可见性、告警对应处置、备份恢复、部署和故障排查 |
| 演进与验证 | 在途任务兼容、迁移/回退、关键承诺的测试、业务质量评测与安全发布 |
| 实施路线 | 增量切片、依赖、验收证据、风险与回退、未决问题、以后升级的条件 |

接口与数据按 [契约设计](contracts-and-data.md) 展开到可实现的程度；不要只写“需要鉴权/数据库/幂等”。未决定语言或数据库时给逻辑结构并标明待选实现点，不伪造精确 DDL。

## 输出约定

开头给推荐方案与理由。默认形成一份工程计划，遵循项目已有路径；用户希望保存且无惯例时可用 `docs/agent-engineering/plan.md`。未要求保存可在对话交付，不强制创建目录。

能力矩阵应可追溯：

| 能力 ID | 本项目承诺/适用条件 | 采用 / 等价覆盖 / 暂缓 / 不适用 | 实际机制与责任边界 | 验收证据或待办 |
|---|---|---|---|---|
| C04 | 例如任务需跨重启恢复 | 采用 | 已选引擎的持久存储与恢复入口 | 中途退出后恢复，已完成动作不重复 |

“暂缓”说明在什么限制下仍可使用，以及何时必须补齐；“不适用”说明缺少哪个触发条件。避免用不适用掩盖当前存在的高风险动作。

实施清单每项至少包含：改变什么行为、影响的组件/数据、前置依赖、验证方法、失败或回退处理。没有时间估算依据时使用相对工作量与不确定性，不编造人天。

第一增量应是符合当前承诺的纵向闭环：接收→执行→交付→失败可解释。不要先建完所有表再接业务，也不要把鉴权、真实写操作的安全、承诺过的持久受理推迟为“以后上生产再说”。高级分区、多区域、训练导出等没有当前需求时可以不实现。

计划应能回答正常怎么跑、失败怎么停或续、谁有权动作、事实存在哪里、怎样证明达到要求、如何降级。只要求规划时到此结束；同时授权实施时明确进入 `/build`。
