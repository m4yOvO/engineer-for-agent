# 接口、身份、状态与数据设计

从使用场景推导协议和存储。以下给设计问题与合同字段，不规定端点、表名或字段必须逐项存在。

## 入口由调用者决定

| 场景 | 可行入口 | 要明确的语义 |
|---|---|---|
| 有界同步能力 | 函数、CLI、同步 RPC/HTTP | 调用截止、取消、输入输出、错误和部分结果 |
| 长时或需持久受理 | 异步命令、任务资源、引擎启动请求 | 接受成功意味着什么、如何取回身份与结果、重复提交 |
| 会话交互 | session/thread + turn/message | 会话与本次执行区别、并发输入、打断/排队、分支 |
| 图/工作流 | 引擎调用、外层业务命令 | thread/workflow/checkpoint 与业务身份映射、暂停/继续、查询 |
| 事件集成 | webhook、订阅、消息 | 来源认证、事件 ID、去重、迟到/乱序、确认和重新交付 |

需要时设计创建/读取/继续/取消/历史/产物访问，但不要强制六个 HTTP 端点。一个已有任务平台的 API 或 CLI 子命令也可以满足合同。

每项接口写清：使用者与可信身份、输入/输出 schema、状态前置条件、原子受理边界、幂等范围/有效期、错误类别、重试建议、分页/流式语义、数据可见性和版本。类型合法不等于业务授权；金额、资源范围等必须按业务取可信值或受权验证。

## 身份至少在语义上分清

| 身份 | 标识什么 | 常见混淆 |
|---|---|---|
| principal / scope | 当前用户、服务、组织或工作区权限范围 | 把请求 body 的 scope 当认证事实 |
| conversation / thread | 一段连续交互历史 | 把每次输入都当新会话，或把 thread ID 当访问凭据 |
| execution / turn / workflow | 一次执行或引擎定义的生命周期 | 因框架命名不同而强行映射为同一类 Run |
| node / task / invocation | 一项逻辑执行单元或工具调用 | 与业务动作的唯一性混为一谈 |
| attempt / delivery | 某次执行尝试或消息投递 | 重试换 attempt 合理，重试换业务身份可能重复操作 |
| operation / intent | 业务上允许发生的一次动作 | 仅用资源 ID，误合并两次合法的新操作 |
| branch / parent / lineage | 分叉、委派、重开与来源关联 | 覆盖旧历史，或泄露其他分支上下文 |

可复用同一个物理 ID，但必须解释为何语义和生命周期一致。只有需要的身份才设计字段。

API 幂等需指定作用域、规范化输入摘要、并发唯一性和保留期。同键同内容复用受理结果，同键异内容按契约拒绝；不要静默覆盖。新业务意图如何创建新身份也要有定义。业务工具幂等期限需覆盖可能的重试/恢复期；下游 key 过期后不能继续假定防重有效。

## 生命周期是协议，不是固定枚举

定义哪些状态/图位置允许哪些动作、由谁触发、并发如何裁决、会产生什么记录，以及停止/等待时资源怎样释放。

状态可以由显式 FSM、图路由、工作流引擎或 actor 行为表示。结束的某次执行历史不应被静默改写；同一 thread 恢复、新 attempt、框架的 retry/reset 或新 execution 都可用，但要明确语义和 lineage。不能把“终态绝不再进入”机械套到框架的 thread 对象，因为 thread 可能容纳多次执行。

单表状态+历史事件可以原子更新；事件溯源则由事件派生投影，不要求再做第二个竞争写入口。远程引擎与本地业务投影不能共用事务时，写明延迟、校准与读者看到的状态。对暂停、继续、取消和完成等适用动作，按 [操作一致性契约](execution-and-recovery.md#操作一致性契约) 展开确认点与失败窗口。

## 从问题反推记录

| 要回答的问题 | 逻辑记录 | 可选载体 |
|---|---|---|
| 现在在哪，结果是什么 | 执行状态、输出/错误、时限、版本 | 引擎查询、业务表、持久对象 |
| 发生过什么，能否解释 | 有关联和顺序/因果的历史 | 事件日志、工作流历史、追加文件 |
| 从哪里继续 | 足够恢复的现场及完成事实 | checkpointer、活动结果、序列化状态 |
| 哪次调用怎样 | 参数摘要/受控载荷、结果、错误、时长、尝试 | 调用记录、Trace、引擎任务历史 |
| 外部到底做了什么 | 操作身份、意图指纹、下游引用、已知/未知结果 | 业务账本或下游权威查询 |
| 花了多少、还能花多少 | usage、估算来源、预留/结算、限额 | 计量日志、预算服务、配额账本 |
| 谁批准或修改 | 可信 actor、动作、对象、理由、版本与时间 | 审计事件、审批记录 |
| 下次应改什么 | 反馈、业务结果、样本、候选及评测 | 文件数据集、平台评测、应用库 |

逻辑区分不要求物理分表。拆分依据是查询、并发、约束、保留时间、权限和写入成本；小规模可以合并，已有工作流记录可直接引用。不要无限制保存完整 prompt/response；受敏感性、允许用途和成本约束。

## 数据合同应可实现

确定实体关系后列出必要字段/类型/可空性/默认值、主键或对象键、唯一/外键/业务约束、并发更新条件、常见查询与索引、迁移和保留策略。

- 操作账本一条逻辑动作，attempt 可多条；同键唯一与同键多尝试不应互相矛盾。
- 索引从访问模式推导，考虑排序/过滤和写成本；已有唯一索引不用重复创建。
- 多租户可通过行过滤、RLS、分库/分 schema、凭据或平台边界实现；检查关联查询、后台任务、对象存储、缓存和向量检索，不强制每表复制 org_id。
- 若承诺某组状态、事件、审计或恢复事实必须共同成立，应以本地事务或引擎的等价原子边界保证。允许延迟的投影与通知另列一致性合同；跨系统用可靠交接与可恢复修复，不能把部分提交说成整体完成，也不能声称本地事务可回滚远程动作。
- 大文件/轨迹可放对象存储，以受控引用关联。考虑校验和、过期/删除、访问权限，以及备份恢复后引用仍有效。

文件/SQLite 是可选生产载体，取决于并发、宿主持久性和恢复目标；换到 PostgreSQL 也不是自动正确。明确锁、隔离、原子写、flush/fsync 或平台确认级别与实际承诺的关系。

## 数据保留与删除

区分短期 prompt、长期审计、业务事实、可重建缓存和备份；设计读取权限、加密、脱敏、归档与清除。追加历史的业务不可变性不等于敏感信息永远不能按政策删除；可用受控删除、脱敏或分离敏感载荷，保留必要审计。

删除/纠正需覆盖记忆、检索索引、产物、导出和副本；保留义务与用户删除请求冲突时，由项目明确政策，不由 Skill 编造通用期限。
