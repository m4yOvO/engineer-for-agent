# 把工程承诺追踪到交付证据

本页维护验证与证据交接；[项目适配记录](engineering-workflow.md#逐条适配与项目记录) 维护选择及理由。两者沿用同一项目条目标识，可合并在现有计划、issue、ADR 或报告中。

## 一条承诺贯穿三个模式

| 模式 | 证据进度 |
|---|---|
| /brainstorming | 承诺 → 拟定合同/拥有者/入口 → 拟验收；不填成已完成 |
| /check | 当前承诺 → 实际入口/配置 → 事实拥有者 → 证据层级与发现 |
| /build | 本次承诺 → 实际改动与调用链 → 运行检查 → 结果及限制 |

记录合同和实现位置、验证环境/命令、关键断言、结果及未知；实现后的证据替换过时假设，保留变更理由。例如发布不得重复，应追到批准内容身份、发布入口、引擎重入边界和实际效果，不能只检查返回成功。

## 纵向增量的完成条件

1. 用户实际入口到结果可走通，适用的认证、持久化、策略与资源控制已注入并生效。
2. 正常和关键失败路径结局可解释；必要守卫发生在动作前，失败后状态与业务效果符合合同。
3. 启动配置、迁移/在途兼容和处置说明与代码一致；缺席依赖指出阻止验证的承诺。

## 故障证据如何选

从相关阶段选会破坏本次承诺的窗口，按适用性观察四类事实：

- 持久状态、历史及可恢复的下一步。
- 真实业务效果或受控 fake 的效果记录，以及动作/尝试身份关联。
- 资源与所有权释放；旧执行者、取消和迟到结果的处理。
- 累计调用、费用和时间；恢复不错误刷新限制。

数量与顺序断言由项目语义决定，不照搬参考中的步骤数、事件数或模型次数。证据注明静态检查、单元、隔离集成、真实依赖验收或生产观测；fake 不能证明真实下游的防重期限、计费、集群和取消行为。失败注入限于已确认的隔离或授权环境。
