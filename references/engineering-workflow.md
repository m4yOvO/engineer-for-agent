# 按工程阶段使用协议

先选择 /brainstorming、/check 或 /build 决定本次可以做什么，再按当前工作选择阶段。阶段不是新命令，也不是必须顺序跑完的瀑布流程；可在一个纵向切片中迭代接口、数据、状态和执行。

## 定位当前工作

| 当前工作 | 协议 | 需要留下的交接内容 |
|---|---|---|
| 确定业务边界和执行架构 | [规划](brainstorming.md)、[架构适配](architecture-adapters.md) | 代表性任务、失败承诺、已有平台责任和适用能力 |
| 定义函数、API、CLI、消息入口 | [接口与身份](stages/interfaces.md) | 调用者、输入输出、身份关联、受理/错误/重复语义 |
| 设计表、对象、索引、历史和恢复存储 | [数据与存储](stages/data-and-storage.md) | 逻辑模型、实际结构、约束、查询、事务、迁移与保留 |
| 设计状态机、图推进、等待与取消 | [状态与生命周期](stages/state-and-lifecycle.md) | 事实拥有者、转移/路由合同、提交边界与恢复矩阵 |
| 接入队列、Worker、平台调度 | [队列与执行权](stages/queue-and-execution.md) | 受理→交接→领取→确认，重试、所有权和积压处置 |
| 接入工具、记录调用、恢复结果 | [工具调用记录与恢复](stages/tool-execution.md) | 决策/调用/动作/尝试/结果关联，提交点、复用与核实 |
| 接入模型、上下文、记忆或检索 | [模型与上下文](stages/model-and-context.md) | provider 合同、消息投影、上下文与记忆边界 |
| 落实权限、沙箱、时间与成本约束 | [安全与资源](stages/security-and-resources.md) | 实际执行门禁、额度拥有者、截止/撤权/释放规则 |
| 展示结果、进度、Trace 或订阅 | [事件与可观测](stages/events-and-observability.md) | 事实来源、游标、水位、可见性、背压与告警 |
| 测试、交付、升级、运行和改进 | [交付与运行](stages/delivery-and-operations.md) | 验证证据、在途兼容、发布/回退、手册与评测 |

完整规划/全面审查遍历 [14 项能力](capability-map.md) 判断适用性，再进入相关协议；局部构建只读受影响协议及必要依赖。队列可以由引擎承担，状态机可以是图/actor/平台历史，存储可以是文件或托管对象，均应解释等价保障。

## 每个阶段怎样完成

每份协议给出适用条件、进入阶段所需事实、设计与实现约定、应整理的产物和验收证据。三种模式使用同一份协议，但交付深度不同：

| 模式 | 使用方法 |
|---|---|
| /brainstorming | 给出可交接合同、拟实现拥有者、取舍与验收；未知标为假设/待核验 |
| /check | 用实际入口、配置和故障证据对照合同；已有等价机制算覆盖，缺少某个文件名不算缺陷 |
| /build | 补齐本次影响的合同，沿实际入口实现守卫/提交/恢复，并运行相应验收；不能只增加字段或接口空壳 |

小改动可把合同与证据写成几行，不强制创建九份文档、执行全套迁移或取得额外批准。用户已有授权继续有效，技术阶段不会切换权限模式。

## 依赖和交接

接口先识别可信身份与业务动作；数据和状态一起确定事实及原子边界；队列把这些事实交给执行者；工具协议处理跨边界效果；模型协议消费可恢复结果。安全、时间和观测贯穿相关路径，交付验证实际配置。

有现成引擎时先核对其责任，再填应用缺口。按 [证据工作流](evidence-workflow.md) 留下“承诺 → 合同 → 实际入口/拥有者 → 验收结果”。每个增量均应形成可运行闭环，允许迭代协议，不要求先建完所有表或全部基础设施。
