# 执行架构适配：统一问题，保留实现自由

先识别当前架构和锁定版本，再决定应用缺什么。下列分类可以组合：一个图节点可以调用 Agent 循环，工作流可以调度多个 Agent，插件宿主可以嵌入图引擎。没有要求把它们统一改造成 while loop。

## 责任映射

对会影响正确性的能力，记录“框架/平台提供什么→启用条件→应用仍负责什么→证据”。不要只根据宣传中的 durable、agentic 或 production-ready 判断。

| 责任 | 可以由谁承担 | 应确认的边界 |
|---|---|---|
| 受理与调度 | 应用数据库队列、Broker、工作流服务、托管 Agent Server、同步调用者 | 受理确认、重复交付、退出/宕机后所有权 |
| 执行进度 | 消息日志、图 checkpointer、工作流事件历史、actor 状态、事务快照 | 持久化模式、完成粒度、可重新进入的代码 |
| 对外任务状态 | 引擎查询或应用投影 | 投影延迟/修复；不能产生两个都可任意修改的权威状态 |
| 外部业务事实 | 下游业务服务、业务账本 | 引擎知道 activity 结束，不等于外部动作未被重复执行 |
| 权限与资源 | 应用策略、宿主、沙箱、平台配额 | 哪个实际执行入口强制执行，是否覆盖扩展和子任务 |
| 观察与审计 | 框架事件、平台 Trace、应用记录 | 可查询/保留/权限是否满足产品承诺 |

## 1. 同步、嵌入式或本地 CLI

适合有界任务、调用者可以等待，或用户明确接受退出即丢失进度的工具。入口可以是函数/命令，不必创建 HTTP Run API、Broker、租约、分布式 Trace。

仍考虑：可中断的调用、输入/输出合同、依赖超时、资源上限、错误与退出码、文件写入完整性、实际工具权限和秘密保护。需要保留结果时，可用文件/SQLite/宿主存储，并核对崩溃时写入与恢复语义。

升级触发条件示例：任务时长超出交互窗口、工作不能丢、要多用户公平调度、多个执行者写同一资源。高风险动作不因本地运行自动免除保护。

## 2. 自定义模型循环

适合需要控制每次模型调用、工具派发、上下文和终止条件的执行器。记录“决策请求、候选动作、已执行结果、最终输出”之间的边界。

恢复不能一律再调模型：已持久化但未执行的动作要先查执行事实；已成功动作复用结果；已保存最终输出只补收尾。多个工具调用时分别关联调用/结果，确定并行或顺序约束。

消息角色、工具协议和 token 流由 provider 适配器负责；不要把某模型的消息序列当成通用协议。持久化频率由恢复承诺、重算成本和存储成本决定，不要求每个 token 或每条消息独立快照。

## 3. 状态图、DAG 与 LangGraph

图中状态可能是 channels/reducers、节点输出、下一批任务和中断；不是一个整数 step_index。先确认并发分支合并、条件边、循环、子图和动态任务的语义。

对 LangGraph 项目重点核对：

- 实际 checkpointer、存储持久性、配置中的 thread/checkpoint/namespace 映射及授权。`thread_id` 不等于身份认证，也不必一一对应某张应用 Run 表。
- checkpoint 与 task writes 的保存边界和 durability 模式；内存 saver、异步落盘与同步落盘的承诺不同。托管 Agent Server 提供存储时先验证现有能力，不重复建 saver。
- `interrupt` 恢复会重新进入所在节点；批准前的代码可能重跑。不要吞掉框架的中断控制流；变更中断顺序时考虑旧等待现场。[官方中断语义](https://docs.langchain.com/oss/python/langgraph/interrupts)
- 分支成功结果、失败分支的重试、reducer 的合并/去重、子图命名空间及并行写冲突。依据当前版本和测试确认 pending writes 的恢复，不自行断言整张图重跑或绝不重跑。
- 图能持久化状态仍不能替外部服务保证一次业务效果。将外部 I/O 放在符合引擎建议的节点/task 边界，并保留业务防重与未知结果处理。
- 图级循环/递归限制、节点重试与模型/SDK 重试的总放大；恢复不会刷新项目级硬预算。

图演进要考虑状态 schema、reducer、节点名称和路由变化。别为表示“等待”在外面再造一套有冲突的全流程状态机；确实需要业务状态时将其定义为投影或独立业务事实。

## 4. 持久工作流引擎

例如 Temporal 的工作流历史和调度可承担恢复、定时等待、子工作流和活动重试。先确认引擎已有保证，应用侧不默认再加 Outbox、Sweeper、任务队列表来复制同一职责。

工作流编排要符合引擎的确定性规则；模型与外部 I/O 放在允许的 activity/task 边界。历史回放使用已记录结果，但未报告完成的活动仍可能重试；所以外部写入仍需要合适的去重/核实。工作流 replay 是运行机制，不是只读 UI 回放。[工作流执行](https://docs.temporal.io/workflow-execution)、[Activity 语义](https://docs.temporal.io/activity-definition)

检查超时、活动重试、心跳、取消、signal/update 重复提交、版本路由、历史增长和结束后如何开始新一代执行。其他引擎可能采用不同术语，不能照搬 Temporal API。

## 5. 插件式 Agent / Coding Harness

可将模型适配、工具、会话日志、执行驱动、策略和 UI 作为独立扩展能力。DeepSeek Harness、Codex、Hermes 与 Pi 提供不同切面，源码入口见 [公开参考](sources.md)。

检查实际扩展接口、依赖顺序、注册作用域、冲突与覆盖授权、卸载清理、可取消调用、错误合同及记录方式。Hook 能观察并不等于能可靠阻止；必须确认动作发生前的强制入口。

会话日志可以是追加文件与分支树，也可以是 SQLite；“没有八张表”不是缺陷。应核对初次写入时点、崩溃尾部、并发写、迁移、保留与导出。宿主安全能力也因运行模式不同：本地 shell、远端沙箱、插件进程具有不同权限。

可扩展性与安全隔离分开。允许加载任意宿主代码的插件通常属于高信任扩展；不能仅凭存在工具注册表就认为插件已被隔离。卸载监听器、进程、连接和后台任务要有明确生命周期。

## 6. 多 Agent、Supervisor 与 Actor

新增问题是委派合同，而非简单加多个循环：任务/消息身份、父子关系、每方输入输出、上下文可见范围、权限衰减、预算分配、并发上限、超时/取消传播、失败汇总、共享状态合并。

子 Agent 返回“已完成”是结果声明，需要相应证据；不能获得超出父级授权的工具权限。多个 Agent 若可能执行同一业务意图，应在业务边界裁决；若是合法的不同动作，不能错误共用一个实体级 key。

Actor/mailbox 模型检查每个 actor 的串行化范围、重启恢复、消息去重与投递顺序；单个 mailbox 串行不自动协调跨 actor 的共享资源。预算与委派深度跨层累计，避免递归扩散。

## 7. 事件驱动、托管服务与混合系统

事件触发、函数计算或托管 Agent 后端要先确认平台的确认点、重试语义、最大时长、并发、状态保留与导出能力。Webhook 入口按实际威胁设计签名/重放保护；事件总线能回放不等于业务工具可重做。

混合架构为每次跨界画清事实与动作。例如工作流 activity 内嵌图：谁持久保存图进度、activity 重试是否重开图、两层超时谁先到、应用收到什么任务标识。选择一个负责跨层恢复的主拥有者，其他层保留可映射的局部身份。

## 防止架构绑死的最后检查

如果建议包含“必须某框架/某表/某服务”，能否换成一个可测的行为保证，并给出已有机制的等价方案？若确实不可替换，说明是用户约束、协议要求还是当前已验证的技术限制。
