# 执行、恢复与外部动作

关注失败窗口和事实拥有者。具体调度和持久化由 [架构适配](architecture-adapters.md) 决定。

## 1. 受理到执行的交接

当承诺“接受后不会因进程退出丢失工作”，受理确认必须对应可恢复的事实或平台确认。

| 实现选择 | 合适前提 | 必须解释 |
|---|---|---|
| 同步直接调用 | 调用有界，调用者承担断线/重试合同 | 连接终止与在途副作用的关系 |
| 单一持久队列/数据库任务 | 一个存储可同时受理和保存调度状态 | 原子领取、重试、确认、清理和容量 |
| 数据库 + 外部 Broker | 两个系统没有共同原子提交 | Outbox/CDC/等价恢复策略；发布成功但本地标记失败会重复 |
| 工作流/托管平台 | 平台承担持久受理与派工 | API 确认语义、连接/配置、任务保留与恢复范围 |

Outbox 是解决一个具体提交窗口的方法，不是每个 Agent 的必备表。若使用它，意图与业务受理同事务，独立发布后再确认；重复发布交给下游去重。任务消息通常带引用和版本，避免携带将过期的权威完整状态；不可变输入快照等场景可以带载荷，说明范围即可。

持久结果先于消息确认；某次消息处理完成不等于整个业务任务成功。已经进入等待或被可靠安排重试，也可以结束本次消息处理。

## 2. 执行权、并发与重试

同一业务状态有并发写者时，需要数据库条件更新、版本/CAS、锁、单写 actor 或引擎等价机制。租约过期只表示没有及时续约，不证明旧进程已死。

自建租约需设计：原子领取、续约、代次/栅栏、过期接管、旧写者拒绝、终止清理。扫描器提交前重新核对条件；旧执行者写入要验证所有权。外部系统不接受栅栏时，依然需要业务防重；两个进程各自认为有权并不意味着能重复动作。

每种失败指定拥有者，避免 API、SDK、节点、Worker 和队列同时做完整重试：

| 情况 | 通常的处理方向 |
|---|---|
| 输入/权限/业务条件拒绝 | 返回明确拒绝，原样重试通常无效 |
| 已确认未执行的临时失败 | 在合同允许时退避、抖动、次数/截止与预算限制 |
| 只读调用超时 | 按业务允许程度有限重试，仍考虑费用和负载 |
| 写操作结果未知 | 根据同一操作身份核实，或按已验证的下游幂等合同重发；否则等待/人工处理 |
| 用户取消或引擎中断 | 按控制流处理，不能吞掉并伪装成功，也不默认当可重试错误 |
| 基础设施损坏 | 保存证据、按调度职责恢复或降级；不要覆盖已有业务事实 |

SDK 内部重试会放大实际次数。定义 attempt 是一次外部尝试、一次节点执行还是一次任务代次，并对整体工作限制累计消耗。耗尽之后保存可排查信息，有明确失败、死信、人工接管或延迟处理出口。

## 3. 持久边界与恢复算法

需要恢复时，列出可能落盘的每一种现场和对应下一步，不只保存 `next_step`。

| 已有事实 | 恢复方向 |
|---|---|
| 仅有已接受输入 | 开始尚未完成的执行单元 |
| 已产生动作意图，未有可靠结果 | 查操作账本/下游事实，不能先生成另一个意图绕开旧动作 |
| 结果已完成，但上下文或状态投影未补齐 | 复用结果并完成本地收尾 |
| 图部分分支已持久完成 | 按引擎恢复语义接续剩余任务，校验 reducer/重复写与合并 |
| 处于等待 | 接受符合当前等待点的输入后继续，不靠常驻线程 sleep |
| 最终输出已保存 | 补终态/投影/通知等收尾，不重新生成业务动作 |
| 数据或版本不可读 | 停在可诊断状态，通过适配或人工处理，不能静默清空重跑 |

Checkpoint 的内容由执行器决定，可包含 channel 状态、消息投影、活动结果、待办动作、预算和配置版本。不是所有框架都需要完整对话快照；也不是写了快照就能消除外部成功、本地未记的窗口。

## 4. 同一业务意图与合法新动作

先定义“业务上只允许发生一次的是什么”。例如发布同一批准版本的报告、提交同一购买请求、给某审批决定执行一次资源变更。仅用实体 ID 可能挡住同一实体的合法多次动作；仅用随机 call_id 则可能放过同意图的重试。

可行身份包括业务命令 ID、实体 + 操作类型 + 业务修订、平台稳定 activity 身份。**如果某个引擎身份确实覆盖所需去重范围，可以使用它**；但若重开 workflow/Run 仍是同一业务意图，就必须把防重身份延续到新执行中。不要绝对禁止所有 run_id，也不要不加分析地用它。

操作合同应包含作用域、意图内容指纹、下游 key/引用、状态、结果、保留期限和冲突处理。逻辑操作唯一，尝试可以多条。命中缓存结果前仍检查访问权限，不能利用旧 key 读他人结果。

本地原子领取防同一入口并发，下游幂等/条件写防外部重复，独立核实处理响应丢失。没有普适的“加 unique 就实现 exactly-once”。若业务接受重复或存在可验证的自然幂等，不必强建同一款账本，但必须解释副作用含通知、审计、费用等是否也可接受。

## 5. 未决外部结果与核实

在可能产生高影响副作用之前，保存足以识别动作的受理依据；调用后记录已确认结果。不要长期持有数据库事务跨外部请求。

请求超时、连接断开、进程退出、网关 5xx 都不能单独证明外部未执行。核实结果至少区分：权威成功、权威拒绝/未执行、仍处理中、查询失败/暂不可见。最终一致系统中的一次“查不到”不等于权威不存在。

未知结果可以通过同 key 查询、webhook、对账任务、受控幂等重发或人工确认收敛；选择取决于下游合同。记录核实时间、证据、修改前后和操作者/系统来源。核实要有幂等/并发控制，并能独立于原执行任务运行；原任务已取消或失败不代表不再需要核实。

补偿是一个新的业务动作，也可能失败或需要授权。它不是回滚历史的时间机器，更不能在诊断模式里自动执行。不可撤销动作没有补偿方案时如实记录限制。

## 6. 等待、批准、取消与委派

人工等待保存具体动作/问题、版本、等待身份、允许回复者和过期政策，释放执行槽。回复与当前等待点绑定，重复回复按合同去重；批准人身份来自认证，不能相信请求中的 `approved_by`。

批准应指向用户实际看过的内容或摘要，包括目标资源、动作、参数与相关版本。批准后改内容需要重新评估。执行前重新核实当前权限、kill switch、业务余额/资源状态等；历史配置快照用于追溯，不能绕过当前撤权。

不要求所有动作审批，低风险自动执行可以是合理政策。涉及并行或多 Agent 时分别定义谁提出、谁批准、谁执行、预算归属和父子取消传播。

取消至少区分已接收取消请求、停止未来推进、外部在途动作已明确结束。实际状态名称自定。取消后可能仍有已发生或未知动作，保留审计并继续核实；不要把按钮“已取消”说成所有外部变化已撤销。

## 7. 四种易混行为

| 行为 | 需明确的合同 |
|---|---|
| 只读历史展示 | 只读记录，不调用模型/工具产生新行为 |
| 引擎 replay / time travel | 依框架可能重入代码、复用结果或继续执行；先核对语义，不等同只读展示 |
| retry / resume / restart | 哪一执行或尝试继续、哪些结果复用、哪些代码可能重跑 |
| rerun / fork / reset / repair | 新意图还是旧意图；历史与 lineage 如何保留；哪些副作用和权限边界不变 |

为 UI 与管理接口使用不含糊的操作名，并提供效果预览；框架名称与产品名称不同是正常的。

## 8. 进度事件与观察器

按场景选 Polling、SSE、WebSocket、RPC stream、回调或终端输出。需要可靠接续时，保存事件或提供等价可重建事实，再通知观察端。

定义事件身份、顺序/因果范围、游标、分页/批量、重复处理、权限和保留。单任务有序不代表所有并行分支天然有全局时间顺序；可以采用单写序号、平台 offset 或可解释的因果关系。

历史转实时要处理订阅与查询间隙；通知是唤醒还是事实本体由所选平台决定。若只是唤醒，需要补偿读取防止丢通知后永远停滞。并发 `MAX(seq)+1` 需要真实协调，不是只靠字段名。

终态展示与最后事件一致；慢客户端有界缓冲和背压/断开恢复。可靠存档事件与临时 token chunk 可以分开，公开字段按授权投影。原生 EventSource 的认证/重连合同、代理缓冲和游标优先级需按实现核对；不要在 URL 暴露长期凭据。
