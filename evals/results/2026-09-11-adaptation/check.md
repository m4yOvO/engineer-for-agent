# 报告发布服务审查报告

当前发布路径存在一个 P1 业务防重缺陷：应用以 workflow 身份生成发布键，换一个 `command_id` 即可为同一文档、同一批准版本再次创建发布物，也可发布该批准版本下的不同内容。平台对同一命令和同一 activity 的复用有效，但其范围不足以覆盖当前业务承诺。

本轮为 `/check`，仅提交审查报告，没有修复项目或旧计划。采用指定 engineer-for-agent Skill 的最终快照；已读取更新后的“逐条适配与项目记录”边界。对应 `references/engineering-workflow.md` SHA-256：`e567e26ec76de563893422a59208f23eb7ef6aa718ed4ee9f63b68e0b894f552`。

## 1. 确定发现

### F01 / P1 / 高置信度 / C02、C03、C06：业务动作身份被缩小为单次 workflow

**位置与证据。** [app.py:13](../../fixtures/item_adaptation/check/app.py) 按 `command_id` 受理，[app.py:16](../../fixtures/item_adaptation/check/app.py) 把 `workflow + ":publish"` 作为下游幂等键。[runtime_fixture.py:15](../../fixtures/item_adaptation/check/runtime_fixture.py) 只在相同命令内比对摘要，并以命令生成 workflow；[runtime_fixture.py:39](../../fixtures/item_adaptation/check/runtime_fixture.py) 只在相同下游键内复用结果或拒绝内容冲突。两层保障都没有按文档与批准版本汇合。

**触发与后果。** 当前要求明确允许用新命令重提旧批准版本（[README.md:5](../../fixtures/item_adaptation/check/README.md)）。隔离检查从真实 `PublicationService.submit` 入口观察到：

- 先提交 `cmd-a/doc-1/rev-1`，再用 `cmd-b` 提交相同内容：返回 `p-1`、`p-2`，fake 效果数为 2；下游键分别是 `wf-cmd-a:publish`、`wf-cmd-b:publish`。
- 保持 `doc-1/rev-1`，第二次改正文并使用 `cmd-b`：没有冲突错误，仍创建 `p-2`。这是同一批准版本内容不可变约束未生效；本轮不据此推断上游认证或批准真实性有漏洞。
- 第一次发布已经生效但响应丢失，再以 `cmd-b` 重试：创建第二份发布物；原 workflow 没有 activity 成功结果，新 workflow 有结果，不能把第二次成功视为找回原发布物。

以上不依赖并发、进程故障或真实服务假设，顺序调用即可复现。三种失败属于同一根因，不能重复计算为三个独立架构问题。没有生产观测，不能宣称生产已经重复发布。

**最小改进选择。** 保留当前 ContractRuntime 受理、调度与 activity 历史合同，在发布边界将稳定业务动作身份定义为本项目的 `publish + document_id + approved_revision`。采用无歧义、带版本约定的编码；将规范化正文/载荷摘要作为此身份下的内容校验条件，而非身份的一部分。这样新命令仍映射同一动作，变更正文命中冲突，新批准版本则有新动作。不能只用文档 ID，否则会挡住合法新版本；不能把正文摘要并入唯一键，否则正文变化会绕过冲突拒绝。

当前 fake 已提供同键同内容复用、同键异内容拒绝，可复用其业务裁决能力；若真实下游提供足够保留期、跨调用原子裁决和权威结果找回，同样可承担该责任，无需先增加独立业务账本。若下游期限短于允许重提/恢复的期限，或旧结果不能找回，则必须补上可持久查询的业务映射、内容指纹和结果引用，或者获得有效业务约定调整；不能单靠换键继续重试。具体载体可沿用平台或现有持久存储，不预先指定数据库及表数。

改动键之前还需确认是否已有旧 workflow/发布物。直接上线新键可能把已用旧键成功发布的版本再发布一次；应制定旧键结果到业务身份的关联、在途任务版本路由或受控核实办法。当前没有旧生产数据证据，这属于修复交接条件，并非本轮已验证的新缺陷。

**验收。** 从实际入口验证：相同批准版本在不同命令、活动重入、响应丢失后均只产生一个发布效果并返回相同发布 ID；同版本异正文拒绝且不增加效果；不同批准版本即使正文相同也可创建新发布物。随后以真实测试适配器补充并发、幂等期限和旧任务兼容验收。修复建议尚未实施。

## 2. 实际路径与可复用保障

当前路径为：可信上游载荷 → `submit` 组成 payload → `runtime.accept(command_id, payload)` → 对应 workflow 的 `publish` activity → `publisher.create(key, payload)` → 下游结果 → activity 历史 → 调用者。

| 事实/责任 | 当前拥有者与接线 | 本轮结论及范围 |
|---|---|---|
| 身份与批准真实性 | 可信上游；README 第 5 行，app 第 1 行 | 按项目已给边界采用；用户明确排除重审，没有独立验证上游实现 |
| 命令受理与命令内容冲突 | ContractRuntime；app 第 13 行、fixture 第 15–24 行 | 同命令同内容复用、同命令异内容拒绝已在内存合同检查中验证 |
| 持久调度与引擎恢复 | 平台合同；README 第 7 行 | 属于平台职责，不能因应用没有自建队列就判为漏派工；真实持久能力本轮未验证 |
| workflow/activity 成功结果 | 引擎历史；app 第 14–17 行、fixture 第 26–30 行 | 同 workflow/activity 成功后重入不再调用 publisher，局部检查已验证 |
| 真实发布事实及同键裁决 | 下游；fixture 第 39–52 行 | fake 同键防重及丢响应恢复已验证；应用键的业务范围存在 F01 |
| 跨命令业务动作唯一性 | 应用应解析业务身份，再由可靠下游/持久机制裁决 | 当前缺失，不能由命令历史自动推导为已有保障 |
| 调用者得到发布 ID | app 直接返回 activity 结果 | 本地路径可返回结果；生产异步受理响应、最终结果查询与保留合同材料不足 |

失败窗口需要分开处理：

| 现场 | 已有机制与正确恢复方向 | 本轮证据 |
|---|---|---|
| 平台已受理，activity 尚未执行 | 由平台持久调度继续 | 责任合同明确；未做真实进程恢复 |
| 下游已创建，响应丢失 | 沿原业务身份在已验证幂等期限内受控重发/核实 | 同命令复用 fake 的 `p-1`；新命令暴露 F01 |
| 下游成功返回，activity 完成尚未记入历史 | activity 重试仍须使用同一业务键；结果不能凭超时视为未发生 | 注入该窗口后同命令恢复，调用两次、效果一次 |
| activity 结果已保存，调用者重试 | 读取成功历史；不为找回结果重新创建 | 同命令两次提交只调用 publisher 一次 |

activity 历史能复用已记录结果，但不能消除“下游已生效、历史未确认”的窗口。当前同命令恢复通过下游同键复用收敛，这项已有保障应保留。

## 6. 工程改进顺序

1. **先修复 F01 并建立回归。** 保持业务版本稳定身份、同身份内容不可变、合法新版本不被合并；复用现有下游幂等和引擎历史。上线前核实旧键和在途任务，避免键切换再制造重复。
2. **核验真实下游保留和找回能力。** 将允许重提/恢复的时间范围与防重事实寿命对齐；缺口用必要的持久业务映射或权威核实补足。明确未知结果出口，不能把超时判成未执行。
3. **验证生产平台职责实际接通。** 检查受理、持久调度、activity 历史、重试、真实恢复及版本路由。继续由平台承担这些职责，不因测试 fake 是内存就重建应用派工。
