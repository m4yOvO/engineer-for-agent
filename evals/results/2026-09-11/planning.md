## P01 本地摘要工具

### 1. 推荐、范围与假设

推荐一个 Python CLI 进程协调输入校验、受限本地推理、结果校验和文件提交。耗时推理放入可终止的子进程，由父进程掌握整个任务截止。无需 HTTP 服务、数据库、队列、checkpointer、多租户鉴权或部署编排。这样直接满足个人使用、允许重跑和维护测试的需求，主要工程成本落在边界清楚、失败不损坏输出。

已知：用户显式指定文本目录；模型已本地部署；禁止网络；没有多用户、自动发布、跨进程恢复要求；中断允许重跑；覆盖既有输出必须显式指定；单次任务需要输入规模和时限限制。

拟定假设：首次版本递归处理普通 UTF-8 文本文件，输出一个 Markdown 摘要文件，按相对路径稳定排序；默认不跟随符号链接，跳过输出文件自身与本次临时文件。具体扩展名白名单、是否递归及模型上下文容量在实现前从本地模型配置确认。可把限制作为安装配置的必填值；示例启动值为累计输入 10 MiB、单文件 2 MiB、最多 200 个文件、任务 180 秒，均为待基准测量的建议值，不是已知模型能力。输出长度上限也必须配置。

模型接入选择：优先复用本地可执行程序或进程内库，在可控子进程内加载现有本地模型资产；不自动下载模型，不作远端 fallback。若既有部署只能通过 TCP/HTTP 接入，严格“无网络”合同下暂不兼容，须先提供本地库/可执行程序或经用户确认可用的 IPC 适配；不得默认为可以访问 localhost 网络。Unix 域 IPC 仅在现有部署具备且能证明取消语义时采用。

两个实际取舍：

| 方案 | 成本和失败语义 | 结论 |
|---|---|---|
| 同进程调用模型 | 最少代码，但阻塞的原生推理可能忽略 Python 取消，无法仅靠线程超时终止消耗 | 只有适配器经验证支持硬取消时使用 |
| 可终止子进程调用模型 | 多一个进程边界，需管理退出和输出大小；能够在截止时结束本次推理 | 推荐，符合“模型可能很慢” |

成功指输入被接受、摘要通过结构与非空校验、完整文件提交成功；摘要事实质量另作人工样本评测。没有吞吐 SLO；先测典型电脑上的峰值内存与 p50/p95 耗时，再调整建议上限。

### 2. 实际入口与代表性路径

拟定 CLI 契约：`summarize INPUT_DIR --output OUTPUT_FILE [--overwrite] [--timeout-seconds N] [--max-total-bytes N] [--max-file-bytes N] [--max-files N] [--max-output-tokens N]`。选项不能超过安装配置的安全硬上限；用户可调小。模型标识指向本地已存在的配置或资产，不接受 URL 或 shell 命令字符串。

身份来自运行 CLI 的本地操作系统用户及明确输入/输出路径；文档内容不能改变这些路径或增加工具权限。stdout 只打印结果路径与简短统计，stderr 打印进度和失败原因，默认不输出源文全文。建议稳定退出码：0 成功，2 参数/输入无效，3 目标已存在且未允许覆盖，4 截止，5 推理/输出校验失败，6 文件提交失败，130 用户中断。错误给出可采取的下一步，不把部分结果作为成功。

正常调用链：CLI 解析与本地配置校验 → 路径与文件枚举 → 按实际读取字节累计限额并形成输入快照 → 模型适配器执行摘要 → 输出校验 → 同目录临时文件完整写入 → 原子提交目标 → 返回成功。所有步骤共享从开始处理输入起算的整体截止。结束前再检查截止，超时不提交迟到结果。

组件及职责：

| 拟定组件 | 输入/输出和作用 | 关键边界 |
|---|---|---|
| CLI/任务协调器 | 配置、退出码、取消信号、剩余时间、最终统计 | 只有它确认整体成功 |
| 文本加载器 | 指定目录 → 有界文本及来源相对路径 | 文件数、单文件/总字节、编码、路径校验在送入模型前完成 |
| 本地模型适配器 | 文本、模型/提示版本、输出上限、剩余期限 → 摘要或类型化错误 | 无工具执行、无网络、无隐式 fallback；拒绝/截断/异常与成功区分 |
| 文件提交器 | 已验证摘要、目标、覆盖许可 → 已提交文件 | 模型不能指定目标；避免半文件和未授权覆盖 |
| 本地诊断记录 | 耗时、模型/配置版本、文件数、字节数、错误类别 | 不持久保存源文、prompt 或凭据 |

失败路径：模型超过剩余时限 → 父进程发终止，经过有界清理宽限仍未退出则强制结束本次子进程组 → 删除本次未提交临时文件 → 返回截止错误，旧目标保持原状。若进程在文件提交前崩溃，允许留下可识别的孤立临时文件，后续仅清理本工具拥有且未使用的临时文件；不自动把它当恢复点。若提交已完成但打印成功前退出，结果可能已存在，重跑默认会明确拒绝覆盖，用户可查看文件后决定。

### 3. 文件与模型合同

输入边界：解析真实输入根；只读取其下允许的普通文件，不跨符号链接到别处；流式读取时再次计数，不能仅依据提前 stat 的长度；防止文件读取期间增大越限。遇到不支持编码、读取失败或输入变化导致快照不一致时，默认整次失败并给出相对路径，避免默默漏掉重要文件。无有效输入视为输入错误。输入目录与输出目录可不同，但输出必须为用户显式提供的本地路径。

输出边界：父目录须已存在且可写；拒绝输出为目录、特殊文件或源文件覆盖。未指定 `--overwrite` 时采用具有原子“不替换既有目标”语义的提交原语，例如同文件系统的临时文件加原子排他安装，不能仅 `exists()` 后普通 rename；验收必须覆盖两个进程竞争同一目标。指定覆盖时才采用原子替换，失败保留原目标。临时文件放在目标所在文件系统，写完整、刷新、校验后提交；是否对文件及目录 fsync 取决于选定操作系统 API。本项目只承诺不暴露写到一半的正式文件，不承诺突然断电零丢失；若要断电持久性，增加该平台上 fsync 与断电恢复验收。

模型输出仅是文字数据。源文本中的“执行命令”“上传”等指令不触发外部行为。适配器须报告使用的模型资产标识、提示词版本、拒绝/截断、返回大小和取消结局；响应超大时中止接收。最小版本默认不作自动重试与自动修复，用户可显式重跑；若以后增加一次受限修复，也必须计入同次时间和输入/输出限制。

无跨调用状态：内存保存任务输入与临时统计；最终文件由用户管理和备份；模型资产和版本化配置由本地安装管理。无需长期记忆、向量库、业务动作账本或历史事件服务。输出中的来源清单可保留相对路径与内容摘要，是否允许保存源文哈希由用户文件保密要求确定。

### 4. 时间、安全与运行

| 边界 | 计时与到期动作 | 承担者/验证 |
|---|---|---|
| 整体任务 | 从输入处理开始按单调时钟计时，不暂停；预留短清理时间，到期不启动新工作、不提交迟到结果 | 协调器；可控时钟及慢模型 fake |
| 单次模型 | 传递整体剩余时间减清理余量，与配置上限取较小值；调用方超时后必须终止本地执行 | 适配器与子进程管理；验证进程树退出 |
| 文件处理 | 每批读取与提交前检查截止，累计实际字节 | 加载器/提交器；大文件与增长文件测试 |
| 用户中断 | 停止新工作，终止子进程，清理本次临时产物，返回 130 | 信号处理器；不能保证操作系统本身卡死时的精准清理 |

禁止网络的保证来自选择不联网的本地适配器，并在隔离验收中观察/阻断出站；不因默认不开 HTTP 就宣称安全。无动态插件、浏览器、任意代码执行或模型选择路径的能力。子进程不继承无关凭据；限制输出、输入和并发为一次一个模型任务。更严格的 GPU/内存硬隔离能力取决于本机环境，当前未验证；先给出保守输入上限、OOM 明确错误及退出清理，不虚构容器已配置。

分发物是可复现的 Python 包/本地启动说明，锁定兼容运行时和依赖，启动时确认模型资产可用；运行不得自动安装依赖。升级记录代码、提示词、模型资产版本。回退程序不会恢复已被用户明确覆盖的文件；重要输出由用户备份。

## P02 图式报告助理

### 1. 推荐、已知合同与关键待核验

推荐保留 LangGraph 的分支、汇总和 interrupt：检索/分析按原图并行 → 汇总成不可变报告修订 → 保存人工等待 → 恢复后校验批准与现行授权 → 独立发布节点。图执行位置、channel/reducer、完成节点写入和恢复现场由现有 checkpointer 管理；应用拥有业务组权限、报告修订/批准事实、发布动作身份、共享时间预算及长期产物。查询用获授权快照与轮询进度即可，不默认引入长连接服务。

已知合同：人工等待最长两天，不计入报告累计十分钟活跃执行预算；interrupt 恢复重入所在节点；已完成节点写入由 checkpointer 管理；外部发布不在 checkpoint 事务内；同一 thread 可创建多份报告；报告库提供请求 key 查询和防重，期限未知；多业务组隔离、取消与继续、进度一天、结果更久、撤权五分钟内停止继续输出。

仅声明“持久 checkpointer 已使用”，未给部署证据。实施前须取得实际 saver/平台绑定、持久介质和保留、确认级别、thread/namespace 映射、并发恢复和恢复接口合同；也须确认平台是否提供持久启动/继续命令。checkpointer 不能自动证明受理到派工可靠。不能据题设宣称已经通过重启验证。

拟定假设：规模为小至中等内部并发，具体峰值、各组公平份额、报告大小、模型/检索供应商及数据地域待测；不强选数据库产品。最终报告、业务索引、批准证据和发布动作记录的保留须覆盖所有允许恢复及业务审计期限，明确大于一天；建议初始结果保留 90 天，仅作待确认政策。图恢复状态至少覆盖两天等待及恢复宽限，不能随一天进度清理。

时间解释的拟定决策：十分钟先按该报告各实际执行工作单元耗时的总和计量；并行分支各用一分钟计两分钟，人工等待、未执行的队列等待和故障停机不增加实际用量；重试、修复、模型/工具等待和工作单元内控制代码均计入。该口径更保守且易强制。若产品希望并行一分钟只计一分钟，应改为共享图活跃区间并集计量，不能只修改显示数字；当前材料未确认这项语义。未知尝试在恢复时保守扣除已预留上限，作为“不可核实消耗”单列，不伪称实际执行过这么久。

### 2. 架构与责任、受理取舍

| 批准决定 | checkpoint 中已消费的等待输入及其不可变审批证据 | 来自认证主体，绑定具体修订、目标与参数 |
| 外部发布是否发生 | 报告库权威事实；应用动作记录保存证据 | 查询、防重 key、未知核实、修正历史 |
| 可用时间与未结算预留 | 报告级预算记录 | 并发原子预留/结算，恢复不刷新额度；checkpoint 引用它而非维护第二份可写余额 |
| 当前展示和一天进度 | 由上述事实构建的应用读投影 | 不可作为任意回写图状态入口；可重建并标明延迟 |
| 现行可见权限 | 组织授权源与强制访问网关 | 旧批准、旧 checkpoint、旧游标均不能绕过撤权 |

两种持久命令实现是同一适配器的可替代后端：优先核验现有平台是否原子接受稳定 command ID 并可靠推进图，满足即复用。若平台只有 saver、没有可靠命令受理，则应用保存 `command_id、report_id、kind、payload_hash、payload_ref、seq、delivery_state`，由最小派工器重试交付，按 report 串行裁决。接收时在本地事务中保存报告索引及启动命令；返回“已受理”后进程退出仍能找到命令。派工成功但确认丢失时以原 command ID 查询/重复交付，图 checkpoint 记录已消费命令身份。执行所有权复用平台序列化合同；若平台不提供，需要代次/CAS 与旧写者隔离后才可多副本运行。命令投递状态只表示交接，不再维护一套竞争的报告流程状态机。实现阶段须在这两条分支中落实一条，不能把未验证的平台能力填成已覆盖。

### 3. 入口、身份与逻辑数据

以下是应用命令/查询契约，可映射到现有 RPC/HTTP，不要求固定 URL：

| 接口 | 可信身份和输入 | 确认点、重复与错误语义 |
|---|---|---|
| CreateReport | 当前用户/服务及组权限；thread_id、主题/来源约束、client_request_key | 持久命令确认后返 report_id、execution_ref、查询引用；同组同 key 同输入复用，异内容冲突；返回前失败或响应丢失用原 key 查询 |
| GetReport / ListReports | 当前读权限；report_id 或 thread_id + 分页 | 返回图位置投影、修订、等待点、预算、发布事实、结果引用与 snapshot_revision；访问拒绝不泄漏他组存在性 |
| ReadProgress | 当前读权限；report_id、cursor/limit | 只读一天内的公开事件；超保留返回 HISTORY_EXPIRED 和获授权快照入口；不重新执行图 |
| ReplyToApproval | 当前有批准权的人；command_id、report_id、wait_id、revision、content_hash、target_hash、决定、可选理由 | 先确认命令持久接收；“批准已生效”须等 checkpoint 条件性消费成功；重复同内容复用，旧等待/过期/异内容/取消胜出明确拒绝 |
| CancelReport | 当前控制权限；command_id、report_id、reason、expected_revision | “取消已受理”与“后续推进已停止”分开；重复安全；未决外部写继续核实 |
| ContinueReport | 当前控制权限；command_id、report_id、指定可恢复原因/现场引用 | 只能继续当前允许的等待/可恢复执行；不复用过期批准、不刷新预算，不自动新建发布意图 |
| CreateRevision | 当前编辑权限；report_id、base_revision、new_content/修改请求 | CAS 创建新不可变修订并失效旧待批准内容；有效新修订重新批准，有独立发布业务身份 |
| GetArtifact | 当前组读权限；report_id、revision、artifact_ref | 走授权网关，禁止仅凭对象 URL 永久访问；返回前和持续传输中执行撤权策略 |

会话 thread 只是交流容器。关系为：业务组 1→N thread；thread 1→N report；report 1→N revision；一次修订可关联多个执行尝试，但同一批准版本及目标只能有一个发布操作；report/revision → checkpoint namespace、artifact、approval、operation、budget。外部用户 thread ID 与内部图 `thread/namespace` 由映射适配器关联。推荐每份报告使用独立图执行命名空间，保留父 conversation_thread；同 thread 的两份报告不覆盖各自等待点和预算。若现有平台仅支持一个活跃图执行，按 report 排队而不是让修订状态混用。

必要逻辑记录如下；物理存储可合并或复用平台，不预设表数量：

- Report：`report_id` 不透明主键，`group_ref/thread_ref/creator_ref` 必填，`created_at`、`current_revision`、`graph_execution_ref`、`schema_version`；有组及 thread 的按时间分页索引。client_request_key 在组/调用者约定范围内唯一，保存规范化输入 hash 和受理结果，保留覆盖客户端重试期。
- Revision：`(report_id, revision)` 唯一，内容与目标不可变；`content_hash`、`target_hash`、`artifact_ref`、来源/模型/提示/图版本清单、`created_by/at`。改变任何批准相关参数创建新 revision，不能原位修改 hash。
- Wait/Approval：等待身份和恢复位置以 checkpoint 为主，含 `wait_id、revision、hashes、allowed_approver_policy_ref、expires_at`；回复事实含已认证 actor、command_id、决定、时间、消费的 checkpoint 引用。审批审计投影如跨库写入可异步补齐，但发布必须读到已持久消费的可信批准证据。
- Operation：`(group, report, revision, target, action_type=publish)` 唯一，`operation_id/downstream_key` 稳定，`intent_hash`、状态/确定性、下游引用、有效期限证据、最后核实时间；attempt 为 1→N，带独立 attempt ID 和错误/结果证据，不用 attempt 或随机模型调用 ID 作为防重 key。
- Budget：每 report 唯一，总额度 600 秒；已结算耗时、各工作单元预留、未知消耗、原子版本。预留 ID 与工作单元/尝试关联，重复结算不重复扣减。使用整数毫秒；默认没有未经需求支持的金额硬预算。
- PublicSnapshot/Progress：快照版本与事件序号由单写器/条件事务分配；同一次公开投影变化与事件在本地共同提交。图 checkpoint 引用防止旧投影覆盖新投影；事件载荷最小化，保留一天，快照和结果依业务期限保留。

组权限必须覆盖关联查询、后台检索、向量过滤、缓存 key、checkpoint 访问、公开进度与产物。group 值从认证上下文和已授权对象关系解析，不能信任请求 body 或模型输出。存储层可使用 RLS、统一强制 repository 或平台隔离机制，但必须从实际入口验证；物理 ID 本身不是访问凭据。

### 4. 图执行、人工等待与操作一致性

正常路径：持久受理 → 解析授权来源 → 检索/分析分支各在预算内执行 → reducer 按分支逻辑键合并不可变结果 → 汇总成 revision → 保存明确等待和 interrupt → 释放执行容量 → 用户批准持久接收 → 图重入审批节点，复用等待身份与内容 → 条件消费批准 → 发布节点复核权限和批准 → 查询/取得发布操作 → 安全发布或复用结果 → 保存图结局和长期产物投影。

interrupt 所在节点在 interrupt 前只能进行纯计算、只读查询或按稳定业务键幂等的准备；不在该位置发布报告或随机生成新的等待 ID。外部发布放在后续独立节点；节点分离仍不能消除“外部成功、checkpoint 未完成”的窗口，所以必须使用业务动作合同。题设允许完成的分支写入复用；应验收实际 reducer、分支键和 pending writes 的恢复，不假定所有并行分支整张重跑。

| 操作 | 前置条件与共同成立的事实 | 确认点/释放与失败下一步 |
|---|---|---|
| 暂停等待 | 当前图所有权；待批准内容/目标已固定；wait_id、revision、过期时间、恢复位置及预算引用共同保存于 checkpoint | checkpoint 确认后才展示可批准并结束该次执行占用；保存失败保持未暂停、可恢复；旧执行者清理须带代次，不得释放新恢复执行者容量 |
| 回复/继续 | 认证批准人符合现行策略；匹配当前 wait_id、内容和期限；回复与取消/过期按同一图所有权/CAS 顺序裁决 | 命令持久化只确认接收；消费回复和下一图位置由 checkpoint 共同记录；唤醒丢失由命令适配器按原 ID 补交，重复不再消费 |
| 取消 | 认证控制人；记录稳定取消命令；与继续/完成的胜者原子裁决 | 用户看到接收、停止未来推进、在途效果已查明三个事实；分支传播取消，释放当前代次资源；晚到外部结果仍记录，不虚构已撤回 |
| 完成/失败收尾 | 最终报告对象先完整写入，checksum/引用可靠；checkpoint 保存结果引用或错误及图结局 | 处理确认和资源释放在可靠保存后；跨库读投影可延迟并重建；重复收尾复用已保存结果，不重新调用模型或发布 |

恢复规则：只持久受理了输入则开始图；部分分支完成则按 checkpointer 接续剩余分支；处于等待则保持等待不占 worker；批准已消费则进入发布节点并复核当前授权；已创建发布操作但结果未知则先查询原 key；外部成功但本地/图未确认则补齐原结果；最终输出已保存则只补投影/收尾；版本无法读取时停止并转人工/兼容处理，不能清空状态重跑。

### 5. 发布治理和取消边界

每个发布 operation 在发出请求前保存稳定 key、批准修订和 intent hash；以唯一约束/条件更新裁决同版本并发。本地事务不跨外部网络调用。报告库是发布事实权威；本地“已发送”或节点返回不能代表业务已成功。

| 窗口/结果 | 下一步 |
|---|---|
| 操作已记录、尚未请求 | 同一 operation 继续；先核对批准、现行权限、预算及防重合同 |
| 报告库成功、响应或本地提交丢失 | 标记未知或保留待核实；按原 key 查询成功后补记录/图结果，不新建 key |
| 同 key 权威查询仍处理中/暂不可见 | 保持未决，退避查询；一次查不到不视为未发布 |
| 查询确认未执行 | 仅在防重仍有效且语义已验证时，用同 key 进行有界重试；否则停止自动写入 |
| key 保留期已过且操作结果未知 | 禁止盲重发；使用永久下游引用/权威证据核实或人工接管。下游合同不足时不能承诺跨该窗口自动恢复且发布一次 |
| 本地已有权威成功 | 当前权限通过后复用结果，任何重开执行仍指向原 operation；不受换 thread/attempt 绕过 |
| 新内容或目标修订 | 新 revision、重新批准、新 operation；保留旧修订 lineage，不能用换 key 给旧意图“解锁” |

重试拥有者：图层管理只读分支的有限重试；模型 SDK 禁用重叠重试或向统一预算报告真实尝试；发布适配器只按以上可确定性规则重试/查询，图节点重入不得直接重发。错误分为输入/授权拒绝、只读临时失败、预算/取消、写入未知、确定业务拒绝。发布 kill switch 可阻止新动作，仍允许授权的只读核实。

取消发生在发布前时阻止发布；发生在网络请求后时只能停止未来推进并跟踪真实结果，不能保证报告未发布。后续撤回若存在属于新的授权业务动作，本计划没有自动撤回许可。人工等待期限从该 wait 的可靠建立时刻计两天；过期回复不得作用于后续等待。重新生成/修改修订不得暗中延长同一等待点或刷新同 report 的预算；需要新任务时显式创建并保留关联。

### 6. 时间预算与资源合同

| 边界 | 拟定计时/截止与到期动作 | 拥有者、传播与恢复 |
|---|---|---|
| 入口请求 | 仅限请求处理；超时不撤销已持久受理命令，客户端按原 key 查询 | 命令适配器；请求 timeout 不作为报告总时限 |
| 排队 | 不扣活跃预算；队列年龄先作告警，用户可取消；审批等待已设期限不得因排队延长 | 平台/派工器；领取时重新检查权限、取消、期限 |
| 报告活跃预算 | 600 秒跨分支、修复、重试、恢复共享；调用前原子预留允许最长耗时；无余额不开始动作 | Budget 是余额权威；实际完成按单调时钟结算，预留/attempt 状态跨重启保存 |
| 单节点/模型/工具 | 单次上限与分配到的剩余预算、批准剩余有效期取最小值，并留收尾余量 | 节点→适配器→SDK 传递；截止后停止输出/启动动作；远端不一定停止，保留未决结果 |
| 并行分支 | 每分支获得不同预留，同一预算 CAS 保证总预留+已用≤600秒；父级控制耗时单列，不能再重复加算嵌套 span | 图调度与预算适配器；争抢失败排队/拒绝，不给每分支完整十分钟 |
| 人工等待 | wait 创建时用权威服务时间保存绝对 expires_at=+两天；不占执行槽、不扣活跃时间 | checkpoint 与平台持久定时器；若无定时器由可恢复到期扫描驱动，扫描提交前条件重验 |
| 所有权/故障恢复 | 已失去执行权的尝试不能开启新动作；本次预留未证明未消耗前不能归还 | 平台 fencing/CAS；未知执行时间保守记预留上限，后续可按可靠证据修正，不重置额度 |
| 观察/产物读取 | 独立短请求时限与授权有效期；观察失败不取消报告 | 查询/授权网关；重连重新鉴权 |

预算整数值和预留均需在调用前接线；只在 trace 汇总耗时无法构成硬限。跨进程不使用旧单调时钟读数，保存可信服务时间的绝对截止、分配时长和尝试身份；本进程用单调时钟计实际用量。时钟偏差容忍须小于剩余截止安全余量，偏差不可判断时拒绝新动作。真实 SDK、平台重试、远端取消和时钟配置均待核验；能保证应用不继续发起/交付越限工作，并不假装客户端超时可撤销已发外部写。

达限：停止新模型/发布调用，保存可见的“执行预算耗尽”及已有草稿/未决操作；只读核实和必要收尾使用单独受控系统维护额度，不被归类为继续生成报告，更不能借维护额度继续发布。外部查询的频率/并发受系统限制，人工等待和取消任务不占模型槽。

### 7. 进度、一天保留和五分钟撤权

默认轮询获授权快照和增量事件。`GetReport` 的 snapshot_revision=H 对应公开投影的一致水位；增量读取从 H 后开始，版本由单写器或事务 CAS 生成，不能 `MAX(seq)+1` 无锁分配。进度事件保留一天，删除时暴露最低可读游标；游标过期返回 HISTORY_EXPIRED、当前快照和结果引用，明确缺少旧历史，不声称已补全。快照后产生的事件仍从 H 后读取；若客户端太久才读取又过期，再取快照。历史展示只读，不调用图 replay、模型或发布。

完成结果、发布事实和报告索引寿命独立于一天事件。隔天用户仍能 `GetReport/GetArtifact`，不能依赖最后一条终态事件还存在。终态公开快照与其最后公开事件在同一本地投影事务提交；图到投影有延迟时显示“状态同步中”和源 checkpoint 版本，由 projector 追赶，不能让旧事件反转新版结果。慢观察器分页、响应大小和频率有界，不阻塞执行。

撤权口径：从授权源确认撤销的时间起，系统在五分钟内停止向该主体继续提供该组的检索内容、生成输出、进度载荷、结果与导出；已传到用户设备的数据无法收回。发布前也复核执行主体及组权限。采用权威撤权通知立即失效缓存，并用周期复核兜底；拟配置传播最长 60 秒、缓存最长 60 秒、持续传输重验最长 60 秒、关闭宽限 30 秒，总最坏 210 秒小于 300 秒，真实链路要验证。权限源不可用且超过短缓存有效期即拒绝新内容输出，不能持续使用旧批准。

不发长期公开下载 URL；网关逐请求授权，若采用签名引用，其有效期及任何 CDN 缓存必须纳入五分钟上界，长下载须周期校验并关闭。执行端在检索前、模型输入/输出交付前、发布前以及长调用的输出边界检查授权；异步核实可由授权的内部服务继续保存事实，但不能将结果传给已撤权用户。若以后采用 SSE，额外落实建立频率/主体连接配额/最大寿命、有界缓冲与慢连接断开、重连鉴权和每段输出校验；这些不是当前轮询方案的必需新增服务。

## P03 持久工作流集成

### 1. 推荐与边界

推荐沿用托管平台的持久受理、调度、活动重试和版本路由；应用仅接入业务命令、稳定发布意图、供应商事件接收、业务投影与独立持续对账。工作流执行完成与供应商 accepted/published/rejected/withdrawn 分开表示。供应商发布后仍可能撤回，因此 published 是当前已确认业务事实，不是永远不变的终态。

已知合同：内部应用启动任务并通过平台查询进度；不需要实时订阅；通知有稳定事件 ID、业务操作 ID、递增资源版本；既有入口验证签名；消息可重复、乱序、丢失；有供应商权威查询；工作流结束后仍可能变化；同一意图重开不可重复发布，合法新修订允许。无须迁移引擎，不增加一套任务队列、Worker 租约或通用执行状态机。

未知项需在计划内显式处理：供应商的提交防重/条件创建能力、操作 ID 是否可在请求前由我方指定、权威查询的一致性及版本合同、撤回最长窗口、资源版本作用域、事件保留与查询历史、各 API 速率、平台启动幂等与历史保留期限、业务数据保留与 RPO/RTO。材料未说供应商具备写入幂等，不能由“有操作 ID/查询”推出“随便重试不会重复”。

拟定假设：内部用户已通过现有企业身份认证；本期是受控供应商内容发布集成，没有新增模型决策路径。若工作流内已有模型，保持其既有活动边界并在实施前补相应模型合同；本计划不虚构模型栈。轮询频率按供应商限额与业务延迟目标配置，初始可用 pending 操作分钟级、已发布活跃资源日级扫描作为试运行建议，所有周期是待测参数，不是已保证 SLO。撤回窗口未知时对仍有效的已发布资源持续扫描，不能在工作流结束或 published 后立即停止。

### 2. 责任分配与正常路径

| 责任 | 拥有者 | 应用需要的证据/补充 |
|---|---|---|
| 启动受理、任务调度、activity 重试、历史回放、版本路由 | 托管平台 | 用真实配置引用和恢复验收确认；不复制 outbox/扫任务表来承担相同职责 |
| 工作流现在在哪/为何结束 | 平台历史与查询 | 应用展示引用；不把结束态改写成供应商最新状态 |
| 一次业务发布的身份、内容、授权、lineage | 应用业务意图记录 | 跨工作流重开稳定；合法修订身份可区分；动作前保存 |
| 内容当前是否已发布/拒绝/撤回 | 供应商权威事实 | 应用投影以供应商版本裁决，保留证据和核实时间 |
| 通知签名与来源认证 | 已有集成入口 | 消费已验证的可信 envelope，另校验账户、操作关联、大小/schema；不重复建设验签系统 |
| 通知去重、修正历史、业务投影 | 应用集成存储 | 本地原子接收、并发归并、留痕，寿命长于单次工作流 |
| 丢消息/晚变化核实、对账游标 | 应用 reconciliation 逻辑；调度复用平台定时任务 | 扫业务事实而非重建执行调度；结束的工作流也覆盖 |
| 进度和结果访问 | 现有内部应用/平台权限边界 | 平台进度与业务状态分区展示；查询仍需现行权限 |

代表路径：应用校验发布命令并提交平台持久启动 → 平台确认后返回 workflow_ref → 首个活动以稳定意图原子建立/复用 operation → 外部写入前校验意图、现行权限及防重前提 → 供应商返回 accepted → 保存“已受理、待业务结果”，平台可等待至首次业务结局或按产品配置结束 → 通知或权威查询确认 published/rejected → 原子更新业务投影、追加历史 → 平台/应用查询分别展示执行进度和当前业务事实。后来收到更高版本 withdrawn，即使原 workflow 已结束，也更新业务投影并追加撤回历史；平台历史保持当时的执行结局。

工作流完成时机可选：等待首次 published/rejected 后结束，用户在平台直接看到发布任务的首次业务结局；或者在 accepted 后结束交接，把后续状态放独立查询。推荐前者以符合“发布任务”直觉，但在供应商长时间无结果时用明确等待期限转人工/结束为“待核实”，绝不写成功。两者都必须保留 workflow 结束后的持续核实能力，不能把工作流永久存活作为唯一接收渠道。

### 3. 命令、操作身份和接口合同

| 契约 | 输入、可信范围和结果 | 并发/重复/失败语义 |
|---|---|---|
| StartPublication | 已认证内部主体；账户/项目、content_id、revision、target、intent_id、规范化内容 hash；返回平台 workflow_ref 和稳定 operation_ref | 平台持久启动确认后才称已受理；响应丢失按稳定启动请求 key 查询；不能先本地返回成功再异步尝试启动 |
| ReopenPublication | 当前控制权限；原 intent_id、原因、原 workflow_ref、不可变内容 hash | 新 workflow generation/执行 lineage，operation/key 仍相同；同 key 异内容冲突；已知 published 复用/查询事实，不重发 |
| StartRevision | 当前发布权限；原 content_id、base_revision、新不可变 revision 与内容 hash | 新修订形成新业务意图，保留父引用；不能把 retry 伪装成新修订 |
| QueryExecution | 当前权限；platform workflow_ref | 使用既有平台接口/授权代理返回执行进度；没有 SSE 和可接续事件流承诺 |
| QueryPublication | 当前权限；operation_ref/content_ref | 返回 latest_confirmed_status、vendor_version、业务事实发生时间、last_verified_at、freshness/争议状态、责任历史引用；不得仅返回 workflow 状态 |
| ReceiveVerifiedNotice | 已验签集成入口交付可信 envelope：provider_account、event_id、operation_id、resource_id、resource_version、status、occurred_at、payload_digest | 持久接收后 ACK；同账户/供应商 event ID 同 hash 去重，异 hash 隔离告警；无关联不能擅自创建发布意图 |
| ReconcilePublication | 授权内部定时/人工操作；operation_ref、reason、可选 expected_version | 只读权威查询并归并，不发送原发布请求；修正与查询失败均留痕；可在任何工作流结局之后运行 |

稳定业务 key 建议语义为 `(provider_account, content_id, revision, target, action=publish)` 或系统生成且与这组不可变事实唯一绑定的 intent_id。不能只用 content_id 阻止新修订，也不能用新 workflow_id/attempt_id 容许同意图重复。工作流 ID 可在同一执行内作幂等启动身份，跨重开必须继续引用原 operation。随机 attempt 是审计粒度，不是业务唯一性。

启动责任：平台已承担持久受理，应用直接依赖其确认；若平台启动接口的同 key 查询/去重合同未提供，实施前先核验并采用平台支持的稳定工作流命名或等价重复受理处理。首次 activity 在外部发布前原子建立业务意图，所以不要求应用数据库与平台启动进行不存在的跨系统事务。多个误重复启动即使存在，也先在 operation 唯一性边界汇合，但这不能代替供应商写入防重。

### 4. 逻辑数据与事务

| 逻辑记录 | 必需字段、约束与关系 | 访问/保留 |
|---|---|---|
| PublicationIntent/Operation | operation_id 主键；账户、content_id、revision、target、intent_hash、actor、created_at 必填；业务元组唯一；稳定 vendor request key/operation_ref；不可变请求快照引用 | 按业务身份查询；保留至少覆盖所有重开、恢复、供应商变更/争议周期；即使归档也保留防重 tombstone/映射 |
| WorkflowLink | workflow_ref/generation 与 operation_id、父 execution、启动命令 key、代码/活动版本引用 | 一 operation 可多 execution；平台拥有执行历史，本地只映射；超平台历史保留时保留必要审计引用或获准导出 |
| DispatchAttempt | attempt_id、operation_id、开始/结束、当前尝试可确定性、vendor_ref、响应/错误证据、请求摘要 | 1→N 尝试；未知不覆盖既有成功；不泄露完整敏感 payload |
| NoticeReceipt | `(provider_account,event_id)` 唯一；可信来源、payload_hash、operation/resource/version、发生/接收时间、处理结论、原始受控引用 | 重复消息无需重复业务历史，但可聚合投递次数；保留期限需覆盖供应商重放期 |
| BusinessProjection | 以供应商资源的正确版本作用域为键；关联 operation/revision；latest_confirmed_status/version、发生时间、证据引用、last_verified_at、next_check_at、freshness、local_revision | 最新状态条件更新；按账户/状态/next_check_at 扫描索引；不把一份报告的新旧修订事实混成全局单状态 |
| BusinessHistory | append-only 的逻辑历史 ID、operation/resource/version、前后状态、来源 notice/query/manual、可信 actor、理由、证据、修正/争议关联 | 原始 accepted、当时 published、后来 withdrawn 均保留；按 operation 时间/版本查责任链 |
| ReconcileCursor/JobState | 调度范围、稳定分页 cursor、扫描代次、last_success、重试/错误、next_run、owner reference | 调度交给平台，应用只持久化业务扫描进度；独立于原 workflow 保留 |

通知本地处理推荐在一个事务内完成：插入去重 receipt → 校验关联及版本规则 → 条件更新投影 → 追加必要业务历史 → 标记 receipt 处理结论 → 提交后 ACK。若处理必须解耦，则先可靠保存 receipt 后 ACK，由可恢复消费任务处理；不要 ACK 后只把消息放内存。原始大载荷如放对象存储，先完整落对象再提交引用，孤立对象可清理；保存必要 hash/签名验证证据引用即可，不复制无关秘密。

未知关联、同事件 ID 不同内容、相同资源版本不同状态进入隔离/争议记录并触发权威查询，不静默丢弃。Receipt 和投影事务失败返回可重试失败；响应丢失导致重投时唯一键安全复用。手工修正只能追加经授权的证据/说明，不得篡改供应商原始通知、旧工作流执行历史或内容修订。

保留期限不能机械用某个统一天数。业务记录、去重身份、通知载荷、责任历史与平台执行历史分别配置：原始敏感 payload 可较早删除/脱敏，但仍需保留供应商版本/状态、hash、操作映射和必要证据。停用项目也要说明仍可能变化的资源由谁核实。备份应覆盖这些记录与产物/证据引用，并验证恢复后不会失去防重历史。

### 5. 供应商异步结果与版本归并

版本次序优先于到达时间。先确认 resource_version 的作用域是资源全局还是每操作；处理器按该作用域串行/CAS 更新。若全局资源版本跨修订递增，建立资源级水位并保留各 operation 的事实：旧修订的新事件可能改变资源当前投影，但不能无关联地改写新修订发布结果。映射不清时保留通知并权威查询，不猜测。

| 收到的证据 | 裁决 |
|---|---|
| version 大于当前已确认版本 | 校验业务允许的状态/关联后更新当前投影并追加事实；若版本跳跃，记录历史有缺口并安排查询/补历史，不凭空补造中间状态 |
| version 小于当前版本 | 保留去重接收/迟到历史，不倒退当前投影；例如 published v2 在 withdrawn v3 后到达，仍显示 withdrawn v3 |
| version 相等且内容一致 | 幂等无业务状态变化；可更新可靠核实时间，不重复追加相同状态变更 |
| version 相等但内容冲突 | 保留双方证据并标记争议，停止自动状态覆盖，权威查询/人工处理 |
| accepted | 只表示供应商受理，不能标 published；可见“等待供应商结果” |
| published → 更高版本 rejected/withdrawn | 按供应商明确语义记录迟到失败/撤回，更新业务投影，保留原先成功事实与责任；不能重发来修正 |
| 权威查询临时失败/查不到 | 保留最近已确认事实及 stale/unknown 标记；除非合同明确证明不存在，不把它改成未发布 |

事件通知按题设是可信业务变化来源，权威查询用于校准。查询也必须带可比较资源版本或等价一致性标识；无版本查询不能用请求完成时刻覆盖已有版本通知。若接口暂不能给版本，串行查询并标记未经版本验证的核实信息；强准确投影保证受到限制，须补齐供应商合同，不能自造本地序号冒充供应商顺序。

### 6. 外部写入窗口、防重与对账

平台会重试未报告完成的 activity；因此发布 activity 每次进入先读取原 operation 并核实可确定性。当前材料不保证供应商写入幂等，采用条件分支：

- 若供应商支持稳定 key 防重/条件创建，确认 key 覆盖账户、意图及所有可能重试/重开期限，同 key 异内容拒绝；每次 retry 使用同 key，响应丢失优先查询，必要重发依已验证合同进行。
- 若供应商不支持这些能力，仅本地 CAS 可以防同时发起，但不能解决“已发布却确认丢失”。发布请求一旦结果不明就禁止自动再发，改为权威查询/人工接管。只有可靠证明未执行且没有旧尝试仍可能生效时才允许恢复原操作。若查询也无法提供这种证据，保持未知，不能声称既能自动恢复又绝不重复。
- 已知 published 的 operation 在重开 workflow 时复用事实并继续业务核实；合法新 revision 才新建 operation。下游保留期届满但本地仍已知成功，不会因重新建工作流而删除该事实。未知结果与过期下游防重并存时禁止换 key。

动作前持久保存 intent 和本次 attempt，再调用供应商；不持有数据库事务跨调用。accepted/published 响应后保存证据，再让 activity 确认完成；若数据库提交失败，平台重试重新进入时按原 key 查询/复用，不能直接重复发送。平台任务取消或失败只停止未来编排，已发请求的核实继续；供应商撤回是后续业务事实或另行授权动作，不能等同应用取消。

持续对账是独立业务核实作业，调度仍交给托管平台：

1. 消费通知快速更新；针对 accepted/unknown、查询过期和有争议的 operation 建 next_check_at，按 provider/account 公平分页扫描。查询请求 ID 与操作 key 分离。
2. 对已 published 的活跃资源定期重新核实，覆盖通知完全丢失及后续撤回；对已 rejected/withdrawn 也在供应商允许再变化的窗口内核对。没有明确最终不可变合同前不能以状态名停止核实。
3. 使用平台持久定时/活动重试处理查询临时错误，应用记录范围/cursor/checkpoint 和结果。每页业务更新可靠提交后再推进游标；进程退出可重扫但不会跳过未提交项；分页排序用稳定复合键或平台支持的快照，避免扫描期间更新 next_check_at 漏项。
4. 每个查询结果进入与通知相同的版本归并器。查询返回同时来了新通知，条件写会拒绝旧版本覆盖；成功核实追加来源、时间、前后、证据，不抹掉历史。
5. 设置每账户并发、请求速率、查询 deadline、退避抖动与单轮工作量；查询超时不会开启新发布。超过陈旧时限/争议时限时告警给集成 owner并移交人工；最近已确认事实仍可见且带过期标识。
6. 终止自动核对只在明确合同成立时：资源被权威不可逆删除/归档且变更窗口关闭，或项目明确批准移交/停止；停止原因和接管人留痕。供应商撤回期限未知时持续低频扫描，超出成本能力须报告无法维持的新鲜度，不能静默视为永远成功。

定时任务是查询业务事实，并非重新调度原工作流任务；无需为平台已有调度再建 Outbox/Sweeper。收件存储的恢复消费若需要平台调度，使用其可靠活动/定时机制，仍保存业务 receipt 的处理状态以支持幂等。

责任历史保留“谁提出哪个修订、谁/哪项策略允许发送、哪个 attempt 发出、当时收到什么、哪个事件/查询改变认识、谁处理争议”。通知 occurred_at 和本地 received_at 分开；接收晚并不代表发生晚。只读对账不自动补偿、撤回或重新发布，也不发送未经授权的用户通知；如产品以后需要通知，只保存待审的通知需求再接入相应授权流程。

### 7. 时间、运维、演进和能力矩阵

入口响应 timeout 只结束客户端等待，已由平台受理的任务仍可查。供应商 accepted 后几小时属于业务等待，不能把短 HTTP deadline 当总业务 deadline。平台持久 timer 负责等待与活动重试，等待释放执行槽。单次 submit/query 活动有有界调用 timeout 和 retry 策略；submit 只有确定安全才 retry，query 可退避重试。初次业务结果超过约定期限时显示 overdue/待核实并移交，不反转成 rejected。既有模型或费用预算若存在由平台/应用原有计量承担；本期按账户限流和次数控制，不额外创建模型网关。

观察只用平台查询进度与业务查询，不设 SSE、事件游标重连或长连接配额。平台历史过期时也应凭 operation 与业务历史查到当前业务状态；如果用户请求的旧执行历史已清理，明确不可用，不能重新执行工作流补历史。查询权限来源于当前企业身份，供应商凭据仅在活动/集成运行环境注入，日志不泄露 payload 或签名秘密。

告警关注 accepted 超期、未知动作龄期、已发布资源核实陈旧、同版本冲突、未关联事件、对账 cursor 停滞、签名入口可信 envelope 缺失/结构异常；由集成 owner 负责，供应商问题交供应商 owner，平台调度问题交平台 owner。运行手册顺序：查 operation/供应商版本/最后证据 → 停止有风险的新写 → 权威查询核实 → 原子修正读模型并追加历史 → 检查实际供应商状态 → 恢复查询或升级人工。禁止“批量重开失败工作流”作为未知发布的处理手段。

沿用平台版本路由，使在途 workflow 继续使用兼容活动代码；业务投影/通知 schema 使用兼容新增，未知字段保留受控原文，不识别状态进入隔离。回退应用版本前确认其可读新记录，必要时保留旧/新处理器和前向修复。回滚代码不回滚供应商发布或历史修正。备份恢复后先只读对账，再开放新写，防止旧备份缺失成功记录导致重发。
