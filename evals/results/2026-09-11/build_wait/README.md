# 持久人工等待模块

使用 /build 修复这个单用户本地 Agent 后端模块。它使用 Python 标准库 SQLite，所有数据和任务都在本地；没有网络、模型 API 或真实发布动作。请沿用现有函数签名和数据库，完成实现与验证，不换框架、不建 HTTP 服务。

当前用户反馈：暂停保存异常后任务无法继续；重复继续有时丢结果；取消和继续竞争时结果难以解释。

项目合同：

- open_db 创建/打开数据库；create 建立 active 任务。
- pause 仅允许 active，保存 waiting 状态、wait_id 和 snapshot；inject_failure 用于模拟保存过程异常。失败不应留下半完成的等待现场，重开数据库后仍应可解释。
- resume 仅接受当前 waiting 的 wait_id；input 是 JSON 值，message_id 是客户端稳定命令 ID。首次接受后状态为 ready，并可靠留下一个可领取 job。同 message_id、task、wait_id 和 input 的重复请求应返回首次结果，不再派工；复用 message_id 改内容应拒绝。
- cancel 仅允许 waiting；取消和继续并发时只接受一个。落败请求抛 ValueError，不允许改写胜者结果。取消不删除历史。
- 错误的 task/wait_id 不得改变任何任务或派工事实。保留操作历史，正常接受的 pause/resume/cancel 各记一次。
- 需要证明调用入口确实使用更新后的实现，验证重开数据库、故障、重复输入和并发竞争。可以增加内部辅助函数及必要约束，不改公开签名。

## 实现与使用

公开入口均在 `service.py`，签名不变。每个写操作独立拥有事务；调用前连接不能有尚未提交的事务。并发调用使用各自通过 `open_db` 打开的连接，SQLite 写锁裁决状态变化。写锁等待沿用 5 秒超时；数据库异常向调用者报告，不当作成功。

- `pause` 在一个事务中检查 active、保存等待身份与 JSON 快照、追加历史。`inject_failure=True` 在状态更新后制造异常，整个事务回滚，可以用相同等待身份重试。
- `resume` 首先查询持久 `commands` 记录。相同命令返回保存的首次结果，即使任务已变为 ready；不同内容复用同一 ID 会抛 `ValueError`。首次受理将 ready 状态、输入、结果、一个 `jobs` 记录和历史一起提交。任务快照仍保留，领取方可通过 job 的 task_id/message_id 查询快照与已接受输入。
- `cancel` 条件性地把 waiting 改为 cancelled 并追加历史。继续和取消竞争时，先取得写锁且成功提交者获胜，另一请求抛 `ValueError`；取消保留快照、等待身份和全部历史。
- 身份参数是非空字符串。输入与快照使用标准 JSON 值；对象键顺序不影响重试判断，数组顺序和 JSON 编码的数值表示保留（例如 `1` 与 `1.0` 视为不同输入）。非有限数字、非字符串对象键等无效值在写入前拒绝。命令 ID 在整个数据库范围唯一，命令记录不自动过期。

未改变原有四张表，也未删除或回填旧记录。旧版本已经产生的半完成等待、重复派工或缺失命令记录没有足够信息自动修复，需要先检查历史和任务现场。不要让旧实现与新实现同时写入数据库。这里保证可靠保存可领取工作；实际 worker 的领取、执行、确认协议不在本模块中。

## 验证

在此目录执行：

```sh
python3 -m unittest -v
```

测试只用 Python 标准库和临时目录中的 SQLite，直接导入本目录公开入口，并核对签名。覆盖保存失败、暂停中进程直接退出、重开数据库、返回结果重放、命令冲突、派工/历史失败回滚、多连接重复受理，以及 30 轮继续/取消竞争。测试检查返回结果和持久状态、输入、派工及历史事实。

未验证断电、磁盘损坏、网络文件系统、多机部署或实际 worker 执行；本模块也不承诺这些能力。
