## 一、check_lifecycle

### 项目事实与实际调用链

产品承诺：受理后重启可恢复；暂停后可继续；从首次受理开始最多 120 秒，排队、重试计入；取消后不能接受该等待点的继续请求。

实际形态是标准库同步函数构成的任务状态服务，没有可访问的模型、工具、Worker、队列或框架执行代码。入口 `start_project` 读取配置，构造只保存路径的 `SqliteStore`，随后把新建字典传给 `TaskService`。`create` 把状态写入该字典；`pause` 改状态并调用外部注入的快照 writer；`resume` 直接更新输入、状态与 deadline；`cancel` 仅改状态。任务事实的实际拥有者是进程内字典。

| 承诺 | 实际入口与拥有者 | 证据与结论 |
|---|---|---|
| 受理后重启可恢复 | `start_project → TaskService({}) → create` | 配置存储未接线；独立进程看不到已受理任务，L1 |
| 暂停后可继续 | `pause → snapshot_writer`，`resume → 字典写入` | 状态先于快照提交；writer 失败留下半完成状态，L2；无恢复读取或唤醒实现证据 |
| 首次受理起 120 秒 | `create`、`resume` 保存 deadline | 首次期限被继续操作刷新；过期继续仍受理，L4 |
| 取消后拒绝旧等待点回复 | `cancel → resume` | 无状态/等待身份前置条件，取消被覆盖，L3 |

### L1 / P1 / 高置信度 / C03、C04、C05、C12

**受理事实没有持久化，重启无法恢复任务。**

**位置与证据：** `check_lifecycle/service.py:6–8` 的 `SqliteStore` 只记录 path，没有存取实现；`:38–41` 虽创建 `configured_store`，实际返回 `TaskService({}, ...)`；`:16–20` 的任务写入仅修改这个字典。`config.json:1` 的 sqlite 配置不是运行保障。探针 `L1_restart` 在一个新 Python 进程中通过真实入口创建 `task-a` 后记录 `["task-a"]`，该进程正常退出；第二个独立进程通过同一配置启动，结果为 `[]`。

**触发与后果：** 创建任务返回后退出进程，即使不是异常崩溃，任务受理事实也丢失。服务不能找到原任务，更无法根据它恢复暂停位置或首次期限。此结论来自实际接线和进程验证，而非因未发现某个数据库或 Outbox 名称而推断。

**改进选择：** 让实际入口使用具备持久读写与恢复枚举能力的存储，并在 create 成功返回前提交可恢复的受理事实；单机场景可实现并接通当前 SQLite 选择，也可复用能保证该合同的宿主或工作流存储。必须同时定义启动恢复与派工交接，不能仅把字典替换成现在这个无存取方法的 `SqliteStore`。规模未明确，不要求额外 Broker、Redis 或固定表结构。

**验证方法：** 使用同一持久位置通过真实入口创建、等待及保存恢复位置，退出并启动新进程，核对身份、输入、状态、快照和原始 deadline，继续到预期下一步；再按实际提交边界测试异常退出。本次只验证正常进程退出后丢失，未进行真实数据库 crash/fsync 验证。

### L3 / P1 / 高置信度 / C02、C03、C04

**取消后的继续请求仍会复活任务；旧回复与重复回复无法裁决。**

**位置与证据：** `check_lifecycle/service.py:28–32` 的 `resume` 不检查当前状态、等待点身份、版本或输入是否已消费；`:34–35` 的取消只写 `cancelled`。探针 `L3_cancel_and_duplicate_resume` 依次执行 create、pause、cancel、resume，记录从 `cancelled` 变为 `active`，且保存了新输入；再调用 resume 会把第一次输入覆盖为第二次输入。

**触发与后果：** 用户对已取消等待点发送迟到回复，即可违反明确的取消承诺。即使调用顺序完全串行也能复现，不需要假设并发。没有等待点标识时，旧等待点回复也无法与后续新等待点区分；并发取消和继续没有共同裁决机制。

**改进选择：** 继续操作须验证当前等待身份、未过期条件和状态，并用原子条件写或等价单写执行器消费一次输入；取消与继续共享该裁决边界。继续成功确认前，应已有可恢复的唤醒依据。已取消、已消费或不匹配的请求应返回明确拒绝或约定的幂等结果。当前只有字典模拟，可先建立这些语义，再由选定存储/引擎承载。

**验证方法：** 取消后回复必须被拒绝且状态仍取消；同等待点重复回复不可覆盖首个已接受输入；旧等待点不能消费新等待点；继续和取消交错时只有一个合法胜者，原输入及必要历史可解释。实际任务调度未提供，本次未验证是否会导致真实工具再次执行。

### L4 / P1 / 高置信度 / C04、C10

**继续操作重置整体期限，且不拒绝已经过期的任务。**

**位置与证据：** `check_lifecycle/service.py:19` 创建 deadline；`:32` 在每次 resume 时重新设为 `time.time() + max_duration`。源码中没有 deadline 比较或到期拒绝。探针 `L4_deadline` 使用可控时钟：首次受理 1000，deadline=1120；时间 1110 继续后 deadline=1230，而 accepted_at 仍为 1000；时间 1300 再继续仍成功，deadline=1420，state=`active`。

**触发与后果：** 每次继续都可延长首次受理起的 120 秒上限，过期任务还能重新进入 active。已保存时间字段没有形成硬截止。排队和重试实现未提供，无法实测其耗时；但现有入口已经明确违反首次受理起固定期限的合同。

**改进选择：** 首次受理时采一次时间并保存稳定的截止依据，恢复和继续保留它；调用前检查剩余时间，把排队、重试以及后续子调用纳入同一期限。领取/唤醒时已到期应终止或按合同返回明确过期结果，不启动新动作。选择存储后说明持久时间来源和时钟偏差处理，执行器还需把剩余时间传给实际调用，并处理到期时未决动作与资源收尾。

**验证方法：** 固定首次期限，在等待、排队、重试及进程恢复后验证 deadline 不变；在到期前、恰好到期和到期后检查新动作启动数及最终状态。当前复现只证明控制入口会延长期限并接受过期继续，没有真实调用可证明执行会被硬停止。

### L2 / P1 / 高置信度 / C03、C04、C05

**暂停状态先于恢复快照提交，失败与交错会留下不一致的等待及释放状态。**

**位置与证据：** `check_lifecycle/service.py:23–26` 先把共享任务标为 waiting，再调用 `snapshot_writer(task)`，最后写 `slot_released=True`。探针 `L2_snapshot_failure` 在 writer 注入异常，pause 抛出错误，但任务仍为 waiting，没有快照成功事实，也没有 slot_released。另一个探针 `L2_late_release` 在 writer 回调内保存等待现场后执行 resume，回到旧 pause 时仍会执行释放标记，最终任务为 active 且 slot_released=True，保存的快照则为 waiting。

**触发与后果：** 快照写入失败时，已发布 waiting 状态不代表任务有可恢复现场，重试/继续无法判断暂停是否完成。writer 内交错继续的复现也说明旧暂停收尾会无条件修改当前任务的释放标记。`slot_released` 只是布尔字段，本次没有证据证明发生了真实执行槽释放；确定的是本地生命周期事实不一致。

**改进选择：** 将等待身份、恢复现场、等待状态及必要交接依据置于一个可验证的提交边界，成功后再确认等待并释放该执行代次拥有的资源；失败不能遗留可被继续消费的半完成等待状态。若快照与任务事实无法同事务提交，可用有明确恢复方向的准备/提交协议；回调、并发及旧执行者清理都要检查对应等待代次/执行权。可复用已有引擎中断合同，无需再造竞争状态机。

**验证方法：** 分别在快照前、写入失败、写入后确认前注入故障，核对任务状态与可恢复现场共同成立；交错 resume/cancel 与旧 pause 收尾，验证旧执行者不能释放或覆盖新代次。后续接通真实调度器后还须实际观察槽位归还和唤醒，不能只看布尔字段。

## 二、check_observers

### 项目事实与实际调用链

产品要求：跟踪供应商实际发布结果及后续撤回，保留历史解释；通知具有递增资源版本；进度订阅可恢复，历史清理后明确告知并提供结果获取途径；撤权后既有订阅不得继续输出。README 已说明 principal 是认证后的身份，floor 是最早保留的事件序号。

实际形态是内存函数构成的结果投影及订阅适配层。`record_submission` 将供应商响应写入 records；`reconcile` 调用注入 lookup，但只查 unknown 记录；`apply_notification` 无条件替换状态/版本并追加通知；`subscribe` 在入口检查 allowed，返回遍历 events 的生成器。供应商是业务结果权威，records 仅是本地投影；events 是注入的历史来源，allowed 是当前权限集合。真实数据库、传输和生产配置不可访问。

| 承诺 | 实际入口与拥有者 | 证据与结论 |
|---|---|---|
| 真实发布结果 | `record_submission → records` | accepted 被直接转成功，O1 |
| 后续撤回持续核实 | `reconcile → lookup` | 成功等非 unknown 状态永不查询，O2 |
| 可解释历史与版本 | `reconcile`、`record_submission`、`apply_notification` | 对账未更新版本或历史、重复提交覆盖历史，O3；旧通知覆盖新状态，O4 |
| 可恢复订阅/历史过期出口 | `subscribe(events, floor, after, ...)` | after 有过滤作用，floor 未使用，O5 |
| 撤权后停止既有输出 | `subscribe → pending_events` | 仅建连鉴权，生成器后续不检查 allowed，O6 |

### O6 / P1 / 高置信度 / C02、C09、C11

**访问撤销后，既有订阅仍输出后续事件。**

**位置与证据：** `check_observers/service.py:21–23` 只在 subscribe 调用时检查 allowed；`:25–28` 的生成器逐个输出期间没有权限校验或撤销联动。探针 `O6_revocation` 为 alice 建立订阅、读取序号 10，然后从同一 allowed 集合删除 alice；旧生成器仍输出序号 11，而新订阅立即抛 `PermissionError("access denied")`。

**触发与后果：** 已建立连接的用户在权限撤销后仍可读取后续受保护事件，直接违反明确访问合同。此处不质疑 principal 的认证来源，也不需要假设真实令牌或网络系统有缺陷；已确认问题是持续授权没有接入输出路径。

**改进选择：** 按撤权合同在事件发送前复核当前权限，或由可信撤权通知使连接失效并停止后续发送。若采用批量检查、缓存或周期校验，应明确撤权生效窗口是否允许；本项目写明撤销后不能继续输出，不能默认容忍无限期旧授权。多副本时需接通可传播的权限版本/撤销事实，具体载体由现有平台决定。

**验证方法：** 建连后首事件前、两个事件间、缓冲有待发送数据时撤权，均不再输出受限内容且释放连接资源；重新连接继续拒绝。本次仅证明内存生成器的撤权失败与新订阅拒绝正常，未验证实际连接清理或集群传播。

### O1 / P1 / 高置信度 / C01、C03、C06、C11

**供应商“已受理”被直接报告成业务成功。**

**位置与证据：** `check_observers/service.py:1–5` 中 accepted 被映射为 succeeded。探针 `O1_accepted` 输入 `{status: accepted, version: 1}`，得到 state=succeeded，而 history 中唯一证据仍是 accepted。

**触发与后果：** 供应商仅接收请求、尚未完成发布时，本地就声称成功；后续实际失败或撤回会使用户看到错误业务结论。下游受理、执行器结束和最终发布在本产品要求中不能等同。

**改进选择：** 保留受理/处理中语义，只有权威发布成功证据才能推进成功投影；保存操作标识与资源版本，后续用查询或通知收敛。无需强制某套状态名，但对外成功必须由业务结果定义。

**验证方法：** accepted 之后分别模拟 pending、succeeded、failed 和 withdrawn；初始不得为 succeeded，每次投影与权威证据一致，且保留初次受理记录。本次没有发起实际发布操作。

### O2 / P1 / 高置信度 / C03、C06、C11

**对账只核查 unknown，无法主动纠正已成功记录及后续撤回。**

**位置与证据：** `check_observers/service.py:8–11` 仅在 `record["state"] == "unknown"` 时执行 lookup。探针 `O2_reconcile_success` 为本地 succeeded 记录提供会返回 withdrawn/version=3 的权威查询 fake；运行 reconcile 后 lookup 调用次数为 0，本地仍 succeeded。

**触发与后果：** 本地已标成功、供应商后续撤回，且对应通知丢失或需要主动核实时，当前对账入口不会发现变化。accepted 的误判成功也因此失去主动修正机会。代码可以处理“成功记录收到新通知”的单条路径，但没有证据表明通知永不丢失，不能据此满足持续跟踪承诺。

**改进选择：** 按供应商终局与撤回合同确定需继续核实的记录范围，包括仍可能变化的成功结果；用现有查询/事件平台提供可靠补查，保存核实位置、时间与结果。不要把修正投影视为重新发布授权。若确实有可靠、可回放且覆盖撤回的通知机制，可用该等价保障，但需要实际接线及恢复证据。

**验证方法：** 本地成功后 fake 改为撤回并故意不给通知，对账应更新当前业务结果并追加历史；同时测试查询失败/暂不可见时不抹除已有可靠事实。本次验证函数选择范围，未验证任何真实调度周期或供应商查询保证。

### O4 / P1 / 高置信度 / C03、C06、C11

**通知没有版本裁决，迟到旧通知会覆盖新事实，重复通知会重复入历史。**

**位置与证据：** `check_observers/service.py:14–18` 无条件应用事件状态和版本。探针 `O4_notification_order` 先写 succeeded/v2，再接收 withdrawn/v3，随后收到迟到 succeeded/v2，最终投影回退为 succeeded/v2；同 v2 再到一次又追加历史。

**触发与后果：** 网络或队列重排使已确认撤回被旧成功覆盖，资源版本倒退。重复投递不去重，历史记录也不能区分“新的业务变化”与“同一通知再次送达”。记录接收顺序本身不能代表资源因果顺序。

**改进选择：** 以同一资源/操作范围的供应商版本作原子条件更新，旧版本不能回退投影；重复版本按既定合同幂等处理。需要保留重复接收诊断时，可记录其为重复/被忽略，而不是又一次业务状态变化。同版本不同内容应保留冲突证据并核实。真实数据库下要用事务/条件写保证并发裁决，不能仅先读后写比较。

**验证方法：** 新版本、旧版本、同版本相同内容、同版本冲突内容及并发交错，验证当前版本不回退且撤回不会被旧成功复活；历史能解释有效变化与忽略原因。本次已复现串行乱序/重复问题，未开展真实并发数据库测试。

### O5 / P1 / 高置信度 / C02、C03、C11

**历史被清理后静默返回剩余事件，没有明确缺口或结果获取途径。**

**位置与证据：** `check_observers/service.py:21–30` 接收 floor 但完全不使用，只过滤 `sequence > after`。探针 `O5_floor` 设置最早保留序号 floor=10、事件为 10 和 11、客户端 after=5，返回普通事件 10、11，没有说明缺失 6–9、重同步水位、结果引用或错误。对照 after=9 时也返回完全相同内容。

**触发与后果：** 断线客户端游标落入已清理区间，会误以为进度历史连续且完整，违反明确的可恢复订阅承诺。若保留事件为空，现有逻辑同样只返回空迭代器，无法区分没有新进度与历史无法接续。

**改进选择：** 根据 last-delivered 游标语义检查保留水位；对于连续序号，after=9/floor=10 可从第 10 条完整继续，after=5 则必须明确不可完整接续，避免把合法边界误判成过期。返回结构化历史过期结果以及当前授权范围内的快照/结果获取途径，并标明其水位和后续订阅办法；不能通过重做发布任务来补展示。

**验证方法：** 对照有效边界 after=floor−1、真正历史缺口、更旧游标及空保留集，核验明确的重同步响应、结果授权和快照至后续事件间无静默遗漏。本次只验证已有 API 的缺口静默行为；结果接口尚未提供，不能验证其真实可用性。

### O3 / P2 / 高置信度 / C03、C06、C11

**权威查询只改状态不更新版本和历史，重复提交同操作还会抹去旧历史。**

**位置与证据：** `check_observers/service.py:11` 只取 lookup 返回的 status，忽略其 version 和其余证据，不追加 history；`:1–5` 对已有 operation_id 整体覆盖记录。探针 `O3_reconcile_history` 从 unknown/v1 经查询得到 withdrawn/v3，记录却变为 state=withdrawn、version=1，history 仍只有 unknown/v1。探针 `O3_resubmission_history` 在已有历史后再次调用 record_submission，原历史被新的单元素 history 替换。

**触发与后果：** 通过查询收敛的当前结论无法由本地历史解释，版本也落后于该结论对应的权威证据；同一逻辑操作再次记录提交响应会删除原有变化路径。缺陷影响产品要求的历史可解释性；重复调用频率和实际生产数据损失未知，因此未按已发生生产审计事故定级。

**改进选择：** 统一查询和通知的事实采纳规则：保存来源、资源版本、核实结果及时间，原子更新当前投影并追加必要历史。相同 operation_id 的重复受理按幂等合同返回/追加解释，而不是覆盖已有历史；合法新业务意图用明确的新身份。历史保留需求不强制独立审计数据库。

**验证方法：** unknown→处理中→成功→撤回的查询路径应具有对应版本与可追溯证据；重复提交不能抹去先前历史；被拒绝的旧事件和查询冲突能解释。当前内存测试验证确定的历史/版本缺口，真实保留、删除与事务保证未验证。
