## S1：个人离线文本摘要 CLI

### 1. 范围、选择与正常路径

已知：个人使用；一个显式输入目录和输出文件；本地模型；没有网络、多用户、跨进程续跑要求；中断允许重跑；未经许可不能覆盖输出；输入规模和运行时长必须有界。

推荐在现有语言中拆分少量职责：CLI 参数与配置校验 → 输入清单与受限读取 → 本地模型适配器 → 摘要校验 → 文件提交器。模型推理可以由可终止的本地子进程承担，编排仍为一个同步任务。无需 HTTP、队列、数据库、持久 checkpoint、租约、审批服务、远程模型 fallback、RAG 或长期记忆。

拟定范围假设：初版处理输入目录直接包含的 UTF-8 `.txt`/`.md` 普通文件，不递归、不跟随符号链接；如确需递归，再以同一目录范围、深度和总量上限扩展。初版每份资料生成带相对文件名的摘要并合成一个 UTF-8 Markdown 文件，不追求任意规模语料的跨文档推理。用户应看到这些限制。

| 方案 | 失败语义与代价 | 取舍 |
|---|---|---|
| 同步任务、内存进度、临时输出 | 中断丢失推理进度；最终文件提交前不影响现有结果 | 推荐，符合允许重跑的承诺 |
| 持久分块缓存/SQLite 续跑 | 需管理输入指纹、模型版本、失效、锁与删除 | 暂缓；昂贵重算或明确提出续跑要求时再引入 |

代表性成功路径：校验全部配置和路径 → 建立有界、排序稳定的输入清单 → 逐文件受限读取/分块并推理 → 校验摘要完整性 → 写入同目录临时文件 → 原子、不覆盖地发布到指定路径 → 输出完成统计并退出 0。任何步骤失败或超时，在提交前停止、清理本次临时文件，返回明确错误；不发布看似完整的部分摘要。

### 2. CLI、数据与文件合同

拟定入口：`summarize --input-dir <directory> --output <file> --model <local-model>`，可另接受本地 `--config`。选定语言后沿用其 CLI 约定。默认没有覆盖行为；初版目标已存在就拒绝，提示用户换路径或自行处理旧文件，不必实现覆盖开关。

- 身份是启动进程的本地用户，不增加账号或请求体中的主体字段。只读显式输入目录和已选择的本地模型/配置，写显式输出及必要的同目录临时文件。输出目录须已存在且可写。
- 输入配置包括有限正数 `max_files`、`max_file_bytes`、`max_total_bytes`、`max_input_tokens`、`max_output_tokens_per_chunk`、`max_output_bytes`、`max_model_calls`、`total_timeout`、`call_timeout`、`cleanup_grace` 和内存上限。所有上限要有单位；缺失、非有限数或越界在读取正文前拒绝。发行默认值由所选模型和目标机器的测量确定，当前无基线，不承诺某台机器的速度或容量；构建首个切片可先要求本地配置显式提供这些值。
- 清单记录相对路径、大小及读取后的内容摘要，按规范化相对路径排序。总量计数在读取中再次强制，文件扫描后的增长不能突破上限；读取失败或解码失败指出文件并终止。空文件可跳过且计入统计，空有效输入拒绝。符号链接、非普通文件、越出目录的路径拒绝；不得无限阻塞于 FIFO/设备文件。
- 输出不能是输入文件或被纳入本次清单；初版可直接要求输出位于输入目录外。目录与文件打开时采用所选平台的安全路径/无符号链接能力，避免仅字符串前缀检查。输入内容只是摘要材料，不执行其中的命令或路径。
- 内存中的事实：本次输入清单、配置版本、调用次数、累计用量、当前文件和截止时间。没有跨进程恢复承诺，不落盘动作账本。输出文件是持久结果，包含摘要、来源文件名及实际模型/配置版本等必要生成信息；诊断信息写 stderr，不混入正文。
- 最终提交：用排他创建生成权限受限的同目录临时文件，完成写入、关闭并校验长度后，调用能原子“目标不存在才发布”的文件系统操作。可用经目标系统验证的 no-replace rename，或同文件系统原子 link 后删除临时名；普通覆盖式 rename 与“先检查再写”均不满足默认防覆盖。两个进程竞争同一路径时只允许一方成功。
- 进程崩溃前未提交，可能留下临时文件；下次运行只报告或清理由本程序格式且明确属于过期任务的临时文件，不删除任意文件。提交成功但退出前崩溃时，结果可以已经存在；重跑应拒绝覆盖，用户先查看结果。仅清理由当前进程持有的临时路径，避免误删其他进程产物。
- 不承诺断电后数据持久性；如以后提出该承诺，另验证文件及父目录 fsync 和目标文件系统保证。结果保留由用户管理，程序不自动删除旧输出或备份正文。

退出合同拟定：0=已提交完整输出；2=参数/配置/输入/目标冲突；3=模型拒绝、异常、截断或摘要校验失败；4=总截止耗尽；5=文件 I/O/提交失败；用户中断使用平台惯例，如 SIGINT 对应 130。错误包括阶段、可理解原因及重跑建议，不泄露全文。进程超时不声明输出不存在，最终文件是否已经提交需要据实报告。

### 3. 状态、调度、模型与工具恢复

| 位置 | 守卫与下一步 | 失败/中断 |
|---|---|---|
| 校验与建清单 | 路径、有限配置、输入类型/规模合法后进入推理 | 不调用模型，不创建最终文件 |
| 推理 | 逐文件/分块执行；每次调用前核对时间、token、次数和输出余量 | 停止后续调用，清理子进程和临时产物 |
| 待提交 | 所有选定输入有完整有效摘要，输出未超限 | 校验失败不发布部分结果 |
| 原子提交 | 用文件系统原子条件决定唯一胜者 | 已存在返回冲突；不能靠重试覆盖它 |
| 已提交 | 确认文件路径和统计后退出 | 收尾异常不再调用模型生成第二份结果 |

调度由同步调用栈承担，默认一次一个模型调用。没有 durable ACK、平台队列或工作执行权记录。单进程计数只能限制本次 CLI，不宣称全机或多实例共享配额。

本地模型适配器约定 `input + immutable model/config version + remaining deadline + token caps → complete text / refusal / truncated / cancelled / error + available usage`。输入超上下文时使用有界分块，每文件最大调用数与总调用数均受限制；不能静默截掉超额正文却声称已完整处理。没有模型自行选择工具或写路径的权限。不接受半截流作为完整摘要；不支持的 usage 指标标为不可用。

时间由 CLI 拥有：入口开始用单调时钟计整体活跃时间，读入、推理和输出均计入；每次调用上限为 `min(call_timeout, remaining_total - cleanup_reserve)`，不足时不启动调用。超时先取消，宽限期后终止本任务模型子进程及其子进程；绑定的库若无法可靠中断，应改用可终止进程隔离。重试默认关闭，未来仅对可解释的只读模型故障有限重试，仍消耗原次数与时间上限；没有远程 fallback。模型推理的内存/线程限制在运行器或操作系统实际执行，不能只在文档声明。

读取与本地推理允许用户重新发起整个任务；这是一份新计算，不是恢复过去的 invocation。唯一需要特别防重的本地写入是最终输出发布，依靠文件提交合同即可，不引入外部操作 key。异常退出后没有模型消息或 checkpoint 要回填。

## S2：已有托管持久工作流的内部资料归档服务

### 1. 承诺、责任与待确认事实

已知：平台合同覆盖持久受理、队列/派工、活动重试、执行历史和版本路由；业务库支持事务。每份资料调用两个归档工具，可能部分成功；每份资料结果必须可查询；通知尽力。明确新版本是合法新意图，同版本恢复不得重复归档。下游有稳定 operation key 防重和权威查询，但期限未给。需要跨天人工确认、取消、当前权限复核和旧任务兼容。

拟定业务完成标准：一份资料的两个工具都被权威确认最终成功才显示“归档完成”；一成功一终局失败显示“部分完成”及逐工具事实；未知或仍处理中显示“待核实/处理中”，不能合并成失败或成功。批次结果是各资料结果的汇总，工作流完成与业务终局分开。取消保留已完成归档；当前未提供删除/补偿能力，不自动补偿。

范围假设：使用已有内部身份体系；按可信 scope 和资料权限隔离。两个工具暂按独立目标建模，允许分别执行和汇总；若 B 依赖 A，改成 B 读取 A 的持久结果后启动，并在 A 拒绝时记录 B 未执行，防重和事实模型不变。未要求模型自动决策，归档为确定性编排，不新增 LLM/多 Agent/RAG；只有后续明确模型加工需求才加载相应执行职责。

| 责任 | 复用/补充 | 确认前提与缺口 |
|---|---|---|
| 持久接收、排队、活动交付、重试、历史回放 | 复用平台 | 已有合同；实际入口、命名空间、持久保留、超时、重试配置和 Worker 接线尚无证据 |
| 执行位置、等待点、控制命令裁决、定时唤醒 | 优先使用平台历史及串行工作流逻辑 | 持久 timer、命令确认/去重/排序、等待释放容量的具体 API 与保证待确认，不能只由“持久”推断 |
| 执行版本路由 | 复用平台 | 老处理器保留、路由规则、历史格式兼容及配置须验证 |
| 资料/归档版本、外部操作、结果与查询 | 应用业务库 | 新增逻辑合同与事务约束；不复制平台队列或独立可任意修改的流程状态机 |
| 归档真实效果、防重和权威状态 | 各下游归档服务 | key 作用域/期限、同 key 异内容、查询可见性/终局性/取消语义需合同验收 |
| 当前权限、批准内容、输入对象、资源限制 | 应用入口与活动执行前门禁 | 平台服务身份不等于用户授权；已有鉴权/上传存储具体实现未知 |
| 通知、结果展示、业务核实 | 应用适配器及平台可调度工作 | 通知失败不改变业务事实；核实可在原执行结束或取消后继续 |

取舍比较：

1. 平台历史做执行事实，业务库保存领域事实，推荐。相较仅从平台历史临时拼查询，能使历史清理后仍有逐资料、逐版本结果，并高效查未决操作；相较自建任务队列/租约/全流程状态表，减少竞争状态和重复机制。
2. 每个资料的每种工具是独立逻辑 activity，推荐；平台自然保存各自活动结果。将两个写工具放进同一 activity 虽少一层编排，却必须在重试入口仍逐操作复用 A、恢复 B，不能整体重做。物理 activity 数可依现有平台约束调整，逻辑操作身份和恢复合同不能合并。
3. 结果采用授权查询与带版本的快照，通知只提示“有更新”。没有持续订阅需求，暂不增加 SSE、WebSocket 或事件网关；页面刷新/轮询即可补偿丢通知。

### 2. 入口、稳定身份与受理顺序

沿用既有服务传输方式，以下是命令语义而非强制 HTTP 路径。可信 `principal/scope` 从认证取得。请求正文不能自报批准人或提升资料访问范围。

| 入口 | 输入与结果 | 前置条件、重复与确认 |
|---|---|---|
| 提交归档批次 | `client_request_id`、schema 版本、有界资料清单（document_id、不可变内容引用/摘要、目标配置）；返回批次/工作流身份和受理状态 | 当前可读资料且可归档；同 scope + 命令类型 + request_id 同规范化输入复用，异内容冲突；收到平台持久受理确认后才报告 accepted |
| 明确创建新归档版本 | 新 request_id、document_id、原版本引用（可选 lineage）、新内容/目标快照，显式 `new_version` 意图 | 再次鉴权；新 request_id 创建新版本，原请求重发仍复用；不能用“恢复”隐式分配新版本 |
| 读取批次/资料版本/操作结果 | 稳定身份、页大小、游标 | 每次当前授权；返回逐工具状态、外部引用、最近核实时间、业务结果版本与执行状态来源；受理后尚未建业务记录显示“初始化中” |
| 回复人工确认 | command_id、wait_id、expected_revision、approve/reject、被展示内容的 digest | 操作者来自认证且属于当前允许批准者；绑定资料版本/目标/参数/工具版本；重复复用命令结果，错等待/变内容/到期返回冲突或已过期 |
| 取消 | command_id、目标批次或资料版本、expected_revision、可选原因 | 当前控制权限；返回“取消命令已受理/已应用”等真实阶段；绝不宣称撤销已发生外部归档 |
| 只读历史与恢复管理 | 历史查询；有权限者显式恢复原版本或请求核实 | 历史展示不调用写工具；恢复延续原版本和 operation key，重发前重新核对权限、期限及未知事实 |

`client_request_id` 由调用者在首发前持有。批次执行身份稳定地映射到 `(trusted_scope, command_type, client_request_id)`；身份只是定位符，不是访问凭据。资料归档版本为独立不透明 ID，稳定映射到 `(batch_intent, document_id)`；不必引入数据库递增版号，展示序号若以后需要可另加。一个批次内重复 document_id 初版拒绝。`document_id` 单独不能作为归档防重 key，因为同一资料允许多个明确版本。

受理选定路径：先完成上传并获得授权的不可变、可持久读取的内容引用，再把完整受理元数据/输入指纹交给平台启动；平台确认即为持久受理点。第一项初始化 activity 用业务库事务幂等创建批次、资料版本、两种逻辑操作和引用。业务库暂不可用只使初始化延迟，平台继续承担恢复，不丢已受理工作。查询按稳定请求身份在缺少业务投影时转向平台的已受理元数据；不把初始化延迟误报为任务不存在。

这条路径不需要“先写业务库后发队列”的双写，故不默认添加 Outbox、应用 Sweeper 或 Broker。构建前须验证平台支持稳定身份启动、重复启动查询和持久输入指纹取回；同 key 异内容必须比较原受理指纹后拒绝，不能静默复用错误请求。若实际平台不能满足这些最小接口合同，须记录具体缺口并重新设计入口交接；仅当不得不先受理到业务库再跨系统启动时，才针对该窗口增加事务受理信封与可靠发布，不取代平台调度。不能在未解决前假定重复受理安全。

上传存储尚未提供部署事实：构建需落实不可变对象、内容完整性、权限和保留。仅本地临时路径不能用于跨天任务；不可变引用失效时停在明确输入不可用状态。未受理上传可按确认过的孤儿清理政策处理；不能在工作流尚可恢复时删除输入对象。入口连接超时只停止等待响应，客户端以原 request_id 查询或重试，不能据此推断未受理。

### 3. 逻辑数据、约束与查询

以下不要求同数量物理表；按既有业务库迁移约定落地。ID/摘要为不可变字符串或明确类型，时间用 UTC 时间点，大小为整数 bytes，revision 为非负整数；枚举值、schema 版本和 nullable 条件必须在选定存储中验证，不写未经执行的伪 DDL。

逻辑 scope 可由受验证的父级关联、查询过滤、既有 RLS 或平台边界落实，不要求每张物理表重复 scope 字段。验收须穿过资料关联查询、后台核实、结果对象和缓存读取，不能只测顶层列表。受控参数/结果引用必须能取回带校验和的真实载荷；摘要只用于一致性核对，不能独自承担恢复。

| 逻辑记录 / 拥有者 | 必要字段、关系、可变性 |
|---|---|
| 受理信封 / 平台历史 | trusted_scope、request_id、principal_ref、input_digest、不可变输入引用、workflow_id、工作流/输入 schema 版本、受理时间；业务库中可有只读镜像，原受理事实不由镜像裁决 |
| 批次 / 业务库 | batch_id、scope、request_id、input_digest、workflow_ref、created_at；1:N 资料版本；可缓存计数与投影水位，缓存可从成员重建 |
| 资料版本 / 业务库 | archive_version_id、scope、document_id、batch_id、lineage_version_id 可空、input_ref/digest、目标与参数快照/版本、created_at、result_revision；1:2 逻辑工具操作；内容/目标改变必须产生显式新版本或重新批准，不能改旧动作指纹 |
| 工具操作 / 业务库 + 下游效果权威 | operation_id、资料版本引用、tool_kind A/B、target_id、stable_downstream_key、intent_digest、tool_schema_version、受控参数引用、status、downstream_ref 可空、latest_authority_version 可空、result_ref/digest 可空、verified_at、next_check_at 可空、dedup_contract_version/有效依据、reconcile_owner；同一版本的每一目标动作唯一 |
| 尝试与核实证据 / 业务库或保留期满足要求的平台 activity 记录 | attempt_id、invocation_id、operation_id、workflow/activity/attempt_ref、工具和参数版本、started_at、finished_at 可空、dispatch/query、发送依据、响应类别、外部 request_ref、结果或错误引用、证据来源；多次尝试追加，不覆盖旧尝试 |
| 等待与命令 / 平台历史 | wait_id、scope/version/actions/digest、允许批准者规则、expires_at、logical_revision、command_id、可信 actor、决定及结果；这是流程控制权威。业务库审计可镜像但不可独立修改控制状态 |
| 当前业务结果 / 业务库 | 每操作当前已核实结论及证据引用；资料汇总由操作结果推导，必要时事务维护缓存；执行位置从平台查询，缓存带水位/更新时间，不作为流程调度输入 |

约束：

- 业务唯一键至少为 `(scope, command_type, request_id)`、`(scope, batch_intent, document_id)`、`(scope, archive_version_id, tool_kind, target_id, action_kind)`；每操作下游 key 唯一且不可更新，参数指纹相同才可复用。key 用域内稳定身份生成并持久保存，不使用 attempt、随机模型 call ID 或每次新建 workflow ID 替换。
- attempt 对 operation 是 N:1，invocation 对 operation 允许 N:1（原意图被不同逻辑调用引用）；每个 invocation 可关联多个 attempts。平台 activity ID 若生命周期覆盖该 invocation 可直接使用，并记录命名空间；重新开执行仍映射原 operation。
- 资料版本必须属于同 scope 的批次与资料；lineage 引用不得跨权限范围。存储外键或应用事务校验均需真实落地。必需键不使用 NULL，大小写/编码规范化在客户端与服务器相同，仍以服务端规则为准。
- “最终成功”必须有可验证下游结果/引用、权威证据及版本或等价顺序依据；“未知”允许没有外部引用，但必须保留原 key 和尝试证据。禁止终态只写字符串却没有结果。业务事实变更使用数据库条件 revision/CAS，不能被迟到投影无条件覆盖。
- 失败和取消不级联删除 operation 或成功结果；重复初始化验证一致后返回已有记录，内容冲突拒绝，不能 upsert 覆盖旧版本。

| 必需查询 | 过滤/排序/索引依据 |
|---|---|
| 响应丢失后找批次 | scope + request_id 唯一查找；缺业务镜像转平台稳定身份 |
| 批次逐资料结果 | scope + batch_id，按不可变 archive_version_id 稳定 keyset 分页；每项返回两个工具事实和 result_revision；并发更新可能跨页变化，刷新即可重新读取，不假称分页事务快照 |
| 某资料的历次版本 | scope + document_id，按 created_at + archive_version_id 排序；包括 lineage，不只保留最新版本 |
| 某资料版本的工具结果与来源 | 版本外键 + tool_kind/target 唯一查询，关联受控证据/下游引用 |
| 待核实操作 | 非终局/争议状态 + next_check_at + operation_id；索引服务于有限批量调度，查询必须包含可操作 scope/权限 |
| 解释一次失败或批准 | operation_id/command_id → attempt/activity/history；Trace 只作链接，不承担唯一恢复依据 |
| 清理与保留 | 按明确 eligibility 时间与仍在途引用过滤；先保证身份/对象不被恢复任务引用，再清理 |

事务/提交边界：

1. 初始化 activity 在业务库一笔事务提交批次、资料版本及操作记录（有界批次才使用单事务；初版入口限制批次大小）。平台完成确认前库事务必须成功；库已成功但 activity 回应丢失时幂等重入。先不调用外部工具。
2. 写工具调用前，一笔短事务核对操作指纹、批准依据和当前授权检查结果，追加 attempt/发送依据；授权服务复核不可由事务假装原子化，见执行门禁合同。数据库事务结束后才发外部请求，不能跨网络持锁。
3. 保存响应时，将 attempt 结论、operation 权威事实/未决证据、资料结果 revision 和需缓存的汇总一起提交；多操作并发合并用行锁/CAS或从操作记录重建，防止计数丢更新。远程写入不能被该事务回滚。
4. 平台记录 activity 完成晚于结果提交；平台历史随后推进或等待。若库已提交、平台未记录，重试读取并复用；平台结果已记但查询投影失败，仅幂等补投影。二者没有分布式事务，也不要求业务库控制平台执行位置。
5. 命令状态/等待消费由同一工作流历史提交，命令审计镜像可异步重建；命令“已应用”不能靠写了审计表就返回。通知在业务结果提交之后尽力执行。

保留分别定义：原始内容/参数、业务结果、操作 key 与必要防重墓碑、尝试证据、批准审计、平台历史、日志、备份。日志可先清理，但查询承诺和未决恢复依赖的事实必须保留。敏感载荷可分离存储、受控删除，必要的身份/摘要与合规留痕按项目政策处理。具体期限、删除授权、备份 RPO/RTO 尚待项目决定；未决记录不得靠自动到期删除消失。备份恢复范围必须包含业务库、输入/结果对象、平台历史关联和核实身份。

### 4. 状态转移与命令一致性

工作流控制位置拟定为：`初始化 → 待人工确认 → 归档活动 → 汇总收尾 → 执行结束`；拒绝/到期走停止收尾，活动结果未知走持久核实或人工交接。每资料可有自己的等待点和并行工具分支，批次父工作流只汇总与传播控制，不以一个布尔值抹平部分完成。

工具业务状态独立为 `未派发 / 在途或结果未知 / 已受理处理中 / 权威最终成功 / 权威最终拒绝或失败 / 无法自动核实需人工`；控制侧可标注取消停止新动作，但已发生的工具事实仍保留。取消标记不能覆盖工具成功。

| 当前位置 + 事件 | 守卫/裁决 | 必须持久成立的事实、确认与资源交接 | 重复/竞争/失败 |
|---|---|---|---|
| 初始化完成，进入等待 | 版本及动作内容固定，等待有有效期和允许回复者规则 | 平台历史保存 wait_id、revision、动作摘要、恢复位置和 timer 后才显示可确认；当前活动结束并释放执行容量 | 等待提交失败由平台恢复；用户回复早到可持久排队，但只在匹配等待点时应用，不能误作用下一等待 |
| 待确认收到 approve/reject | 可信 actor、当前 wait_id/revision、未过期、内容 digest 一致；同工作流串行裁决 | 同一历史事务/平台等价边界记录命令结果、条件消费等待并可靠安排下一步；随后确认 applied | 同 command_id 同内容返回原结果，异内容冲突；旧等待/旧版本/过期输入拒绝；不能先消费输入后靠临时线程唤醒 |
| 任意可控位置收到 cancel | 当前控制权限，按当前逻辑 revision 与结束事实裁决 | 历史记录取消请求及停止后续推进的决定；待确认时关闭等待，在执行时请求取消并保留在途操作列表 | 与继续在等待点竞争由历史顺序和条件状态产生唯一胜者；批准先赢后取消仍可停止之后动作，不能追溯撤回已派发调用 |
| 等待/整体截止触发 | 平台时间及当前 wait/revision，排除已完成旧 timer | 记录过期决定，停止新动作；未决外部操作交给核实/人工责任人；释放容量 | 过期回复不恢复新等待；旧 timer 不能取消新版本 |
| 工具活动完成/失败 | operation、attempt、schema 与当前事实匹配；权威证据有效 | 先提交库结果，再完成 activity；工作流按记录结果推进/有界重试/核实 | A 成功不因 B 失败回退；迟到 A 证据仍保存但不重新推进已取消流程 |
| 所有可执行步骤已处理，收尾 | 每资料都有结果或明确未决交接 | 业务结果/错误可靠可查后记录执行结局，平台 ACK/释放；通知独立 | 收尾重复幂等；输出已保存只补收尾；未决交接不冒充业务完成 |
| 未知 schema/旧代码不兼容 | 版本路由/读取适配失败 | 保留现场并显示需处理，禁止静默重置状态 | 交由旧处理器、兼容适配或明确人工迁移；不换 key 重跑 |

平台若只有持久 signal 而无同步 applied 返回，则入口明确返回“命令已持久接收”，客户端用 command_id 查询最终裁决；仅在结果已经进历史时返回“已应用”。须实测平台命令受理/排序/唤醒保证；未核验不写成原子能力已通过。活动不能在等待期间常驻 sleep。已释放的旧活动或旧代次清理不得修改新等待、释放新执行容量或重写新控制状态；执行权管理由平台负责，应用只做业务事实条件合并。

批准内容包括资料版本、内容 digest、两工具目标、规范化参数与工具 schema/policy 版本。任何影响动作的变更使原批准失效并创建新等待身份。审批决定前和每个真实 dispatch 前均复核当前资料/目标权限、工具启用开关、批准有效性、业务条件与剩余预算；恢复、重投与读取缓存结果同样检查当前访问权。当前身份权限与历史快照分开。

权限撤销与在途请求不能凭空原子化：门禁是调用前最近一次可信授权判定，记录其时间/策略版本；若产品要求撤权立即阻断已经取得授权的调用，必须由下游在实际执行点校验短效授权/策略版本。当前材料未提供此保证。门禁发现撤权时停止新写入；仍可由明确授权的服务核实既有动作，但不能向已撤权用户暴露结果。

### 5. 队列、活动与时间责任

受理 → 平台持久历史 → 平台派工 → activity 读取不可变引用与 operation → 执行前门禁 → 提交工具结果/可恢复未知事实 → 平台 activity 完成确认 → 工作流推进/持久等待。传递逻辑字段为 workflow/activity 身份、资料版本/operation 引用、输入/schema 版本、调用限额和截止；消息里的主体引用不是直接授权。

| 情况 | 唯一重试/调度责任 | 应用仍需做的事 |
|---|---|---|
| 平台投递重复、Worker 失联、ACK 丢失 | 复用平台活动调度及执行权 | 原 invocation/operation 不变；复用库结果；晚到证据条件合并 |
| 确认未执行的临时失败 | 平台 activity 策略承担有限退避/抖动与次数 | 适配器返回明确可重试分类；SDK 完整自动重试默认关闭或纳入同一总预算 |
| 输入/权限/业务拒绝 | 不自动重试原请求 | 保存可查询拒绝；需要新授权/输入才能改变下一步 |
| 写入超时或结果不明 | 核实流程，不当普通失败无限 retry | 按同 key 查询；仅在确认仍有效的下游防重合同内受控同 key 重发 |
| 跨天等待 | 平台持久等待/timer，能力需实测 | 保存批准身份、期限和恢复依据；活动结束释放容量 |
| 取消、截止 | 平台停止未来派工并传播取消 | 保留真实结果及未决操作，核实可独立继续 |
| 通知失败 | 通知适配器有限尽力尝试 | 不回滚业务事实，不令归档 activity 为通知再执行 |

核实使用现有平台的独立持久工作/子工作流或平台定时任务，按 operation 稳定身份去重调度；业务库可提供到期操作查询，平台负责派发与重试，不自建第二套 Worker 租约。若已有核实工作，将响应丢失恢复到同一核实身份。取消业务主流程不能连带取消未决核实责任；核实失败耗尽时进入有明确 owner 的人工队列/可查询状态，而非销毁事实。

容量先按批次资料数、单资料 bytes、scope 在途批次、每工具并发及速率上限配置；多副本限额由平台全局配额或下游已验证配额承担，不能把本地 semaphore 当全局保障。平台队列最老任务年龄/待审批时长/未决操作年龄用于定位与告警，阈值须依据约定和测量。工具 A/B 是否共享限流范围待确认。初版不引入跨区、额外优先级队列或 Kubernetes。

时间合同（具体数值待业务和下游合同确定，必须有限、持久且配置后才能启用）：

- 入口超时仅终止等待响应；已受理继续可查。
- 整体归档版本保存 wall-clock 截止，人工等待计入；审批可跨天，不能套用请求秒级超时。平台持久时间是跨恢复依据，不从进程单调时钟恢复。活动资源另按累计调用/活跃消耗限制。
- 每等待点保存 expires_at；到期停止新写入并交代已有效果。当前需求未给天数，不能声称某个等待时长已经受保障。
- 排队年龄可有软告警；资料有效期/整体截止是硬守卫，领取时检查，排队重投不能获得新期限。
- 工具调用使用本次上限与剩余总预算中的较小值，并预留保存结果时间。超时只表示停止等响应，不能证明下游停止；剩余预算不足不启动新写入。
- 平台/SDK/工具尝试数统一计算；恢复沿用原版本预算。合法新版本可有新预算，但不能用于绕过原版本未决操作。
- 自动恢复窗口、下游 key 防重期、权威查询/结果保留期共同决定允许重发的时间范围。首次可能发送时间已记录时不能重置计时；期限临近先停止可能超出保障的新尝试并转核实/人工。

### 6. 工具执行事实与恢复算法

每个工具适配器要给实际合同：受控输入与 schema、目标身份/权限、写入效果范围（含附带通知/收费等）、同 key 同内容的返回语义、同 key 异内容冲突、key 的命名空间与起算/保留期限、权威查询的可见性/不存在证明/终局性、结果引用保留、取消与超时语义。工具 A 与 B 分别验证，不因一个服务符合就推定另一个符合。

此项目没有模型决策层。事实关系为：`平台持久受理/编排位置 → invocation(activity逻辑身份) → operation(资料版本+工具目标动作) → attempts → 持久结果/核实证据 → 原 activity 结果与资料查询投影`。工具协议内的 provider call ID 不适用；下游 request ID 仅用于关联，不能替代 operation key。

执行步骤：

1. 初始化持久化完整两工具动作集合及版本/参数引用。重入从历史和库读取，不重新推导另一批动作。
2. 解析原 operation，复核当前权限、批准、key 期限、内容指纹及剩余时间。已有最终结果则授权后复用；存在任何可能发出的无确认尝试则进入核实。
3. 允许新调用时先短事务记录原意图、invocation 与 attempt 依据。平台可能重投并发执行，数据库唯一约束防止创建第二个 operation；所有允许的外部尝试使用同一个已保存 key。应用不重新实现平台执行租约；真正防外部重复依靠已验证的下游同 key 合同。
4. 事务外调用工具，返回后保存结构化结果/拒绝/处理中/未知证据。任何“prepared/准备发送”记录都不能证明未发出，崩溃可能在实际发送后、改标记前。
5. 结果事务完成才回应 activity。重试先复用已存结果，再给平台补 activity 完成/结果投影，不能为修复缺失返回重新归档。两工具结果按各自 invocation 关联，不按到达顺序串接。
6. 可确认最终状态后更新业务读模型与 revision，再尽力通知；工作流只消费已持久结果。业务事实若仍非终局，可靠安排核实或人工责任后结束本次 activity。

| 恢复时已有事实 | 下一步与拒绝盲区 |
|---|---|
| 平台已受理，库初始化未完成 | 重试幂等初始化；查询显示初始化中，不重复受理 |
| 两操作已建立，没有可能发送的 attempt | 当前门禁通过后执行原 operation |
| 有准备/发送依据，没有可靠响应 | 视为可能已执行，按原 key 权威查询；不能由标记断言未执行 |
| A 已最终成功，B 未开始/临时失败 | 复用 A 及其结果；B 在原 key/批准/预算下继续；实际 A 效果数不得增加 |
| A 成功，B 未知 | 复用 A；只核实 B，不把整个版本换新 key 重跑 |
| 下游已执行，响应丢失或本地落盘失败 | 查询原 key/外部引用；权威成功补回原结果；仍在处理则等待；查询失败/暂不可见保留未知 |
| 权威确认未执行 | 在明确允许重试且 key 仍有效、当前权限和预算通过时执行同 key；不能因一次最终一致“查不到”进入此分支 |
| 库结果已持久、activity 完成或汇总投影丢失 | 幂等补平台结果/查询投影，结果来源和 revision 可核对，不再调用写工具 |
| 原流程取消/结束后返回迟到结果 | 保存原 operation 真实效果与证据；不恢复被禁止的新动作；核实责任继续 |
| key 已过期、保留期不明或查询证据冲突 | 停止自动写重试，保留未决与最后已知事实，转权威核实/人工；更换 key 不构成恢复 |
| 结果对象损坏、schema 无法读、历史缺失 | 显示恢复限制，使用权威查询或兼容处理器；不以空结果完成，也不重做写入来补档 |

本地唯一约束不能证明远端 exactly-once。当前“同版本不重复归档”的保障必须同时依赖稳定操作身份、正确恢复路径及两个下游在全部可能重试期内有效的防重合同。期限未确认前，可构建隔离原型和验证本地协议，但不能启用不受保护的真实写入重试并宣称承诺满足。

### 7. 终局核实、通知与可观测

下游“请求成功/已受理”只有在合同明确为最终业务成功时才直接终局。否则保存 accepted/processing，依据权威查询收敛到最终结果。收到通知只触发核实或携带经验证的证据，不由到达时间裁决事实新旧；验证来源、scope、operation 对应及下游版本/因果顺序。重复事件去重；旧失败通知不能覆盖新的成功；没有可比较版本时查询权威状态并保留冲突证据。

已标成功也要确认其终局含义：若下游允许撤销/后续失败，在约定时间内继续核对并追加修正记录，更新业务结果、保留原调用历史。若权威合同确认成功不可逆且最终，则停止周期核对该操作。一次查不到不反转已确认成功。没有终局期限或查询不可用时，限制核实频率/次数并转人工，不能无限占用 Worker。核实发现失败不自动重发写入；补偿若今后需要，应作为另行授权的新业务动作。

查询快照含业务 revision、逐操作状态/证据时间及独立执行位置来源。通知只含获授权的最少信息/结果链接，通知丢失通过刷新/轮询结果解决；不要求可靠通知 Outbox。平台历史过期后业务结果仍应按自身保留合同可查；若历史或结果已依政策清理，返回明确不可用及保留说明，不能启动业务来补展示。

观测关联 scope 的受控标识、batch/version/operation/invocation/attempt、工具与流程版本；日志不含原文、凭据或无权限的结果。指标包括已受理但未初始化、活动积压、批准超期、逐工具错误、未决年龄、核实耗尽和查询可用性。阈值依据测量，指定归档服务 owner 分诊：先查稳定 key 与最后证据 → 停用相关新写入 → 受控权威核实 → 验证业务投影 → 必要时联系下游 owner；不能用批量重跑作为通用修复。

上线前仍需确认的少数架构关键事项：两工具是否依赖；各自 key 起算/有效期、查询可见性和终局性；平台命令/稳定启动/等待 API；身份系统和不可变上传存储；审批范围/期限及整体墙钟截止；结果、历史及备份保留，容量目标与运维 owner。这些未知不阻止本计划和隔离构建，但阻止相应真实保障的验收与声明。没有依据提供人天、吞吐或可用性数字。
