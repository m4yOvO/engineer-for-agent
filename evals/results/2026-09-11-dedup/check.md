# 报告发布服务审查

当前确定缺陷是发布动作的身份范围过窄：`app.py` 用 `workflow + ":publish"` 做下游幂等键，而 workflow 来自 `command_id`。同一批准版本换一个命令重新提交时会创建第二份发布物，也会接受同版本下变更后的正文。工作流的重复受理与 activity 结果复用已有明确合同，应保留；修复重点是让业务发布身份跨命令稳定，并维持批准版本与内容的一致性。

本次执行 `/check`，只读审查 [项目需求](../../fixtures/item_adaptation/check/README.md)、`app.py`、`runtime_fixture.py`、`old-plan.md`，没有修改项目或调用网络/真实服务。项目没有提供依赖锁、生产入口、平台配置、真实下游合同及灾备证据；本次目录范围内没有可识别的分支/提交信息，因此以文件哈希记录工作区快照，不向父目录追查仓库元数据。复现脚本与输出均放在项目外的 `behavior/`。

## 1. 确定发现

### F01 · P1 · 同一批准版本跨命令重复发布

- **置信度：高。能力：C02/C03/C06；状态：已发现缺陷。** `app.py:10–16` 接受业务载荷后，以命令建立 workflow，再以 workflow 生成下游键。`runtime_fixture.py:15–24` 仅按 command 去重；`runtime_fixture.py:39–48` 仅按传入的下游键去重。因此同一 `document_id + approved_revision` 使用新 command 会落到新 workflow、新下游键。
- **实际触发与影响：** T02 从实际 `PublicationService.submit` 依次提交 `c1/doc-1/r1/approved text` 与 `c2/doc-1/r1/approved text`，产生 `p-1`、`p-2`，效果数为 2，下游键为 `wf-c1:publish` 和 `wf-c2:publish`。这违反 README 明确的“一份发布物”及新 command 找回原发布物要求；无需并发就会发生。未据此推断生产已经发生事故。
- **丢响应放大：** T07 首次调用在 fake 创建后丢响应，应用尚无成功 activity 结果；用户以新 command 重试再次产生 `p-2`，效果数 2。相反，T06 沿用原 command 能找回 `p-1`，说明现有下游与引擎保障确实有作用，只是作用域不足。
- **最小修复：** 在发布入口从可信业务参数派生稳定操作身份，例如版本化编码的 `(publish, document_id, approved_revision)`，将该身份转换为下游键，不能包含 command、workflow 或 attempt。仍沿用平台受理和 activity 历史；新的 command 可有新的 workflow，但所有对应 activity 都指向同一发布动作。键编码应避免字符串拼接歧义；如实际服务还有明确目标或租户作用域，需按可信合同纳入，不能由本轮凭空新增。真实下游必须原子保证同键同内容复用并覆盖所有并发执行者和允许重试期。
- **替代与代价：** 若平台能用业务身份持久地唯一受理、校验内容并跨 command 查询同一 workflow，可采用该等价机制，但当前 ContractRuntime 材料仅保证按 command，不能直接假设支持。下游保留范围不足时，需要持久业务索引/账本补齐跨命令身份与原结果查询；这不是另造派工系统，且单有本地唯一约束不能消除远端响应丢失窗口。
- **修后验收：** T02/T07 效果数都为 1，调用者得到同一 publication ID；同版本并发新命令仍只有一个效果。T04 新批准版本必须仍产生新发布物，不能仅以 document ID 去重。

### F02 · P1 · 新命令可绕过同批准版本正文冲突检查

- **置信度：高。能力：C02/C06/C09；状态：已发现缺陷。** `app.py:11–16` 将正文放入 payload，却没有把 `document_id + approved_revision` 绑定到固定内容。当前摘要校验分别位于 command 边界（`runtime_fixture.py:16–20`）和下游键边界（`:40–44`），两者都随新 command 改变作用域。
- **实际触发与影响：** T03 在 `doc-1/r1` 已以 `approved text` 发布后，使用 `c2` 提交 `changed text`，没有报错并创建第二份发布物。上游身份/批准真实性已被用户明确排除出本轮；这里审查的是服务自己的同版本内容不变合同，不能用上游可信替代该合同。
- **最小修复：** 与 F01 共用稳定业务键，对固定规范编码的 `document_id、approved_revision、body` 计算内容指纹；同业务键但正文变化返回清晰冲突，不产生新效果。正文比较应保留当前内容精确性，除非项目另行明确规范化规则，不应通过空白折叠等处理把变化隐藏掉；更不能把 body 哈希追加进业务键让变化成为“新操作”。现有 PublisherFake 的同键异内容拒绝可直接复用。若有业务索引，唯一占位与指纹检查必须原子完成，不能先读后无条件写。
- **替代与代价：** 下游长期原子冲突检测可独自承担效果边界，不强制新增应用表；若需要长期查询、超过下游键期限或关联多个 workflow，则保留稳定键、内容指纹、原结果/下游引用和必要载荷的持久业务记录。该记录的生命周期需要与业务防重承诺一致。
- **修后验收：** T03 明确冲突且效果数保持 1；相同 command 改内容的 T05 继续拒绝；两个新 command 同时以不同 body 提交同版本时至多一份生效，另一方得到冲突。F01/F02 是两个独立合同的失败，共享同一个修复增量，风险不重复计数。

## 5. 改进顺序与交接

1. **优先修复 F01/F02，形成一个发布闭环。** 由发布模块负责人定义稳定操作键及精确内容冲突规则，从 `submit` 实际传到下游，保留引擎命令去重和历史复用。先让 T02/T03/T07 按修后合同通过，同时保留 T01/T04/T05/T06/T08。补并发同内容/异内容检查；并发保证需落在实际下游或持久存储的原子约束上，不能以单线程 fake 推论。
2. **在接入/放量前补齐平台和下游合同。** 平台负责人提供 U01/U04 的配置、确认点、查询和重试证据；下游负责人提供 U02/U05 的期限、原子性、权威结果及终局性。如果当前服务已运行，先核对历史映射并控制旧路径继续产生新风险；本轮没有执行停用、发布或其他外部操作。
3. **实施兼容切换与未决处理。** 先识别同批准版本的旧发布事实及未决尝试，再安排旧 workflow 排空/版本路由和键别名。若发现一版本已有多份或多正文，保存冲突证据并由业务确认有效发布物；不得自动删除或重发来“修复”。SDK/引擎采用一个明确的重试计划，失败后的人工入口需能按稳定身份定位原效果。
4. **用真实接线完成服务验收及运行交接。** 在受控环境验证持久受理、响应丢失、activity 重入、历史查询、键期限边界与在途兼容；按实测数据定时限/容量和未决处置。只在真实返回会后续变化时追加持续核实。无需为通过审查引入 Kubernetes、独立事件系统、模型层或与平台竞争的状态/调度系统。

验收完成条件是：同一批准版本在用户新命令与平台重入下都找回同一最终发布物；同版本改正文拒绝；新版本合法发布；未知效果按原身份收敛；异步受理和结果查询有真实持久平台证据。当前报告完成了审查与隔离复现，尚未修复上述缺陷，也未宣称生产可用。
