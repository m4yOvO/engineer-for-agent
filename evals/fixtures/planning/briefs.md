# 三个独立项目

以下均为虚构需求。分别使用 /brainstorming 形成可交接的工程计划，解释组件作用和关键验证，不写实现代码。未给出的规模参数可列假设，不需要等待提问才能交付。

## P01 本地摘要工具

个人电脑上的 Python CLI 从用户指定目录读取文本，用已部署的本地模型做摘要，输出到本地文件。不访问网络，没有多用户、自动发布或跨进程恢复需求。中断允许重新执行，覆盖既有输出必须显式指定。模型调用可能很慢，要有单次任务的时限和输入大小限制。用户希望可维护、可测试，不打算部署服务。

## P02 图式报告助理

已有 LangGraph 形式的状态图：检索和分析可以并行，汇总后请求人工批准，再向企业报告库发布。保留图架构；用户可在同一个 thread 发起多份报告。项目资料声明已使用平台的持久 checkpointer，但没有提供部署核验记录。

人工等待最长两天，不计入一次报告累计十分钟的活跃执行预算。批准后进程可能重启；同一个批准版本只能发布一次，修改后的新版本可以再次发布。报告库提供按业务请求 key 查询及防重功能，具体保留期待确认。平台约定：interrupt 恢复会重新进入节点；完成的节点写入由 checkpointer 管理，外部发布结果不在其事务内。本题按这些合同规划，不需要查最新框架 API。

需要多个业务组访问隔离、任务进度展示、取消与继续。历史进度只保留一天，最终报告保存更久；用户隔天回来仍要能看结果。授权撤销应在五分钟内停止继续输出该组内容。请规划入口/数据关系、执行与恢复、时间策略、发布治理和验收。

## P03 持久工作流集成

现有托管工作流平台已承担持久受理、任务调度、活动重试和版本路由。内部应用启动供应商内容发布任务，通过平台查询进度；不需要实时订阅。沿用平台，不迁移引擎。

供应商返回 accepted 后可能几小时才给 published 或 rejected；也可能在发布后通知撤回。通知带稳定事件 ID、业务操作 ID 和递增资源版本，签名由已有集成入口验证。通知可能重复、乱序、丢失；供应商也提供权威查询。需要维护准确业务投影和责任历史，工作流结束后仍可能收到变化。同一业务意图重开工作流不能重复发布，合法新修订应允许。请规划应用与平台的责任、数据与接口、对账流程、故障验证和交付证据。
